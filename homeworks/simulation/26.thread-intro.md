# 1: Let’s examine a simple program, “loop.s”. First, just read and understand it. Then, run it with these arguments (`./x86.py -t 1 -p loop.s -i 100 -R dx`) This specifies a single thread, an interrupt every 100 instructions, and tracing of register %dx. What will %dx be during the run?

```bash
./x86.py -t 1 -p loop.s -i 100 -R dx

#    dx          Thread 0
#     0
#     -1   1000 sub  $1,%dx
#     -1   1001 test $0,%dx
#     -1   1002 jgte .top
#     -1   1003 halt
```

# 2: Same code, different flags: (`./x86.py -p loop.s -t 2 -i 100 -a dx=3,dx=3 -R dx`) This specifies two threads, and initializes each %dx to 3. What values will %dx see? Does the presence of multiple threads affect your calculations? Is there a race in this code?

# 4: Now, a different program, looping-race-nolock.s, which accesses a shared variable located at address 2000; we’ll call this variable value. Run it with a single thread to confirm your understanding: `./x86.py -p looping-race-nolock.s -t 1 -M 2000`. What is value (i.e., at memory address 2000) throughout the run?

```bash
./x86.py -p looping-race-nolock.s -t 1 -M 2000

# 2000          Thread 0
#     0
#     0   1000 mov 2000, %ax
#     0   1001 add $1, %ax
#     1   1002 mov %ax, 2000
#     1   1003 sub  $1, %bx
#     1   1004 test $0, %bx
#     1   1005 jgt .top
#     1   1006 halt
```

# 5: Run with multiple iterations/threads: `./x86.py -p looping-race-nolock.s -t 2 -a bx=3 -M 2000`. Why does each thread loop three times? What is final value of value?

- Why does each thread loop 3 times:
  - Initial value of bx in each thread is 3.
  - Each iteration decrement bx.
  - After 3 iterations, bx becomes 0, and the `jgt` instruction is not executed (condition: bx > 0).
- What is final value of `value`:
  - Initial value of `value` (at address 2000) is 0.
  - Each iteration load `value` to ax, increase it by 1, and store it back to memory.
  - 3 iterations per thread, 2 threads, no interleaving -> `value = value + 3*2 = 0 + 6 = 6`.

# 6: Run with random interrupt intervals: `./x86.py -p looping-race-nolock.s -t 2 -M 2000 -i 4 -r -s 0` with different seeds (-s 1, -s 2, etc.) Can you tell by looking at the thread interleaving what the final value of value will be? Does the timing of the interrupt matter? Where can it safely occur? Where not? In other words, where is the critical section exactly?

- Yes, the timing of the interrupt matters. It is safe outside of the critical section.
- The critical section is this block:

```asm
mov 2000, %ax
add $1, %ax
mov %ax, 2000
```

- Example problem:
  - T1 completed `add $1, %ax` -> mem[2000] = 0, ax(T1) = 1
  - interrupt.
  - T2 completed `mov %ax, 2000` -> mem[2000] = 1, ax(T2) = 1
  - interrupt.
  - T1 completed `mov %ax, 2000` -> mem[2000] = 1, ax(T1) = 1
  - Expected: mem[2000] = 2.

# 7: Now examine fixed interrupt intervals: `./x86.py -p looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 1`. What will the final value of the shared variable value be? What about when you change -i 2, -i 3, etc.? For which interrupt intervals does the program give the “correct” answer?

```bash
./x86.py -p looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 1
# -> value = 1

./x86.py -p looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 2
# -> value = 1

./x86.py -p looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 3
# -> value = 2
```

- With interrupt interval = 3, the program give desired answer.
- Explanation: Each thread has 1 iteration, where the first 3 instructions form the critical section.

# 8: Run the same for more loops (e.g., set `-a bx=100`). What interrupt intervals (-i) lead to a correct outcome? Which intervals are surprising?

- Instructions executed in each iteration:

```asm
mov 2000, %ax
add $1, %ax
mov %ax, 2000

sub  $1, %bx
test $0, %bx
jgt .top
```

- The critical section contains 3 instructions. Each iteration contains 6 instructions, which is a multiples of 3
  -> We will **always** receive desired result if interrupt interval is a multiple of 3.

# 10: Now switch the inputs: `./x86.py -p wait-for-me.s -a ax=0,ax=1 -R ax -M 2000`. How do the threads behave? What is thread 0 doing? How would changing the interrupt interval (e.g., -i 1000, or perhaps to use random intervals) change the trace outcome? Is the program efficiently using the CPU?

- Thread 0 is waiting for mem[2000] to becomes 1. It keeps "spinning" until thread 1 finally set mem[2000] to 1.
- The program is not using the CPU efficiently (waste CPU cycles). It should have used a condition variable so thread 0 can sleep then be notified.
