# 8: Now let’s look at the code in peterson.s, which implements Peterson’s algorithm (mentioned in a sidebar in the text). Study the code and see if you can make sense of it

- Equivalent C code:

```c
int flag[2];
int turn;
int count;
// ...

// acquire
flag[self] = 1; // self is current thread ID (0 or 1)
turn = 1 - self;

// critical section
count = count + 1;

// release
flag[self] = 0
```

# 11: Now study the code for the ticket lock in `ticket.s`. Does it match the code in the chapter? Then run with the following flags: `-a bx=1000,bx=1000` (causing each thread to loop through the critical section 1000 times). Watch what happens; do the threads spend much time spin-waiting for the lock?

```bash
./x86.py -p ticket.s -a bx=1000,bx=1000 -c
```

- Equivalent C code (a bit different with lecture):

```c
for (int i = N; i > 0; i--) {
    // acquire lock
    my_turn = FetchAndAdd(&ticket);
    while (turn != my_turn)
        ; // spin

    // critical section
    count = count + 1;

    // release lock
    // (lecture use: turn = turn + 1;)
    FetchAndAdd(&turn);
}
```

- After T1 acquires the lock:
  - If a context switch happens before T1 releases the lock, T2 will just spin for the entire time slice.
  - If T1 can execute all remaining instruction, it goes back to lock acquiring and spin for the rest of the time slice (since now it's T2's turn).
- The threads spend a large amount of time spin-waiting:
  - The interrupt interval is 50 (instructions).
  - The number of instructions after acquiring the lock: 3(critical section) + 2(release lock) + 3(check if still looping) = 8 (instructions).

# 13: Now examine `yield.s`, in which a `yield` instruction enables one thread to yield control of the CPU (realistically, this would be an OS primitive, but for the simplicity, we assume an instruction does the task). Find a scenario where `test-and-set.s` wastes cycles spinning, but `yield.s` does not. How many instructions are saved? In what scenarios do these savings arise?

- Equivalent C code:

```c
for (int i = N; i > 0; i--) {
    // acquire lock
    while (TestAndSet(&mutex, 1) == 1)
        yield(); // give up the CPU

    // critical section
    count = count + 1;

    // release lock
    mutex = 0;
}
```

- Example scenario where `yields.s` perform better than `test-and-set.s`:

```bash
# . 2 threads.
# . each thread executes 100 iterations.
# . interrupt interval = 20 (instructions).

./x86.py -p yield.s -a bx=100,bx=100 -i 20 -c
./x86.py -p test-and-set.s -a bx=100,bx=100 -i 20 -c
```

- Explanation:
  - T1 acquires the lock successfully and hasn't released it.
  - Interrupt -> switch to T2.
  - T2 tries to acquire the lock and failed.
    - `yield.s`: T2 gives up the CPU right away -> switch back to T1.
    - `test-and-set.s`: T2 keeps spinning for the entire time slice.
  - Number of instructions saved: 20 - 6 = 14.

# 14: Finally, examine `test-and-test-and-set.s`. What does this lock do? What kind of savings does it introduce as compared to `test-and-set.s`?

- Equivalent C code of `test-and-test-and-set.s`:

```c
for (int i = N; i > 0; i--) {
    // acquire lock
    while (mutex != 0 || TestAndSet(&mutex, 1) != 0)
        ;

    // critical section
    count = count + 1;

    // release lock
    mutex = 0;
}
```

- What does it do:
  - Reduces the number of instructions needed to check that the lock is already acquired (4 -> 2).
  - Incurs additional cost if the lock is actually free (4 -> 6).
- But I don't think it's useful since we're using spin-waiting _(the thread will used up the entire time slice anyway)_.
