# Problem

- Paging requires an extra memory lookup for each memory reference.

# Solution

- Hardware support: Add a **translation-lookaside buffer** (TLB).
- A TLB is part of the chip's **memory management unit** (MMU), and is simply a hardware **cache** of popular virtual-to-physical address translations.

# TLB Basic algorithm

```python
# Assumptions:
# - linear page table (is an array)
# - hardware-managed TLB

vpn = (virtual_addr & VPN_MASK) >> SHIFT
success, tlb_entry = TLBLookup(vpn)

if success == True: # TLB hit
    if can_access(tlb_entry.protect_bits) == True:
        offset = virtual_addr & OFFSET_MASK
        physical_addr = (tlb_entry.pfn << SHIFT) | offset
        register = AccessMemory(physical_addr)
    else:
        raise Exception(PROTECTION_FAULT)

else: # TLB miss
    pte_addr = PTBR + (vpn * sizeof(PTE))
    pte = AccessMemory(pte_addr)
    if pte.valid == False:
        raise Exception(SEGMENTATION_FAULT)
    if can_access(pte.protect_bits) == False:
        raise Exception(PROTECTION_FAULT)
    else:
        TLBInsert(vpn, pte.pfn, pte.protect_bits)
        RetryInstruction()
```

- TLBs rely upon spatial and temporal locality for success, which are program properties.
- Example: accessing array

# Who handles TLB miss

- 2 candidates: hardware, OS

## Hardware-managed TLBs

- Hardware handle TLB miss entirely.
- **Algorithm**: see [TLB Basic algorithm](#tlb-basic-algorithm) above.
- **Complexity**:
  - Hardware must know exactly where the page tables are located in memory (via a **page-table base register**).
  - Hardware must know the exact format of the page tables.

## Software-managed TLBs

- **Algorithm**:

```python
vpn = (virtual_addr & VPN_MASK) >> SHIFT
success, tlb_entry = TLBLookup(vpn)

if success == True: # TLB hit
    if can_access(tlb_entry.protect_bits) == True:
        offset = virtual_addr & OFFSET_MASK
        physical_addr = (tlb_entry.pfn << SHIFT) | offset
        register = AccessMemory(physical_addr)
    else:
        raise Exception(PROTECTION_FAULT)

else: # TLB miss
    raise Exception(TLB_MISS)
```

- **Flow**:
  - On a TLB miss, the hardware simply raise an exception, which pauses the current instruction stream, raises the privilege level to kernel mode, and jumps to a **trap handler**.
  - The trap handler is code within the OS that handles TLB misses. When run, the code will look up translation in the page table, use special privileged instructions to update the TLB, and return from the trap.
  - The hardware retries the instruction, resulting in a TLB hit.
- **Important details**:
  - The return-from-trap instruction is different. Hardware must resume execution at the instruction that caused the trap, not the instruction after it -> Hardware must save a different PC when trapping into the OS depending on how a trap or exception was caused.
  - Finding the TLB miss-handling code can cause infinite chain of TLB misses. -> Keep the TLB miss handlers in physical memory where they are **unmapped** and not subject to address translation, or reserve some permanent translation slots in the TLB for the handler code.
- **Advantage**:
  - Flexibility: The OS can use any data structure it wants to implement page tables, without necessitating hardware change.
  - Simplicity: On TLB miss, the hardware just raise an exception and let the OS TLB miss handler do the rest.

# TLB Contents

- A typical TLB might have 32, 64, or 128 entries and be **fully associative** (any given translation can be anywhere in the TLB, and the hardware will search the TLB in parallel to find the desired translation).
- Example TLB entry: `| VPN | PFN | other bits`
- **valid** bit: whether the entry has a valid translation or not.
  - important: TLB valid bit != PTE valid bit
- **protection** bits: determine how a page can be accessed (as in the page table).
- other fields: **address-space identifier**, **dirty bit**, ...

# TLB issue: context switches

## Problem

- When context-switching, the translations in the TLB for the last process are not meaningful to the about-to-be-run process.

## Solution 1: Flush the TLB on context switches

- With software-managed TLB: use an explicit and privileged hardware instruction.
- With hardware-managed TLB: the flush could be enacted when the page-table base register is changed (the OS changes the PTBR on a context switch).
- In either case, the flush operation simply sets all valid bits to 0.
- Cost:
  - Each time a process runs, it must incur TLB misses.
  - If the OS switches between processes frequently, this cost may be high.

## Solution 2: Enable sharing of the TLB across context switches

- Some hardware systems provide an **address space identifier** (ASID) field in the TLB (entries).
- ASID is like **process identifier** (PID), but usually it has fewer bits.

# Issue: replacement policy

- 1 common approach: evict the **least recently used** (LRU) entry.
- another typical approach: evict a TLB mapping at **random**.
