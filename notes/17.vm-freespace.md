# Problem: external fragmentation

- The free space gets chopped into pieces of different sizes; subsequent requests may fail because there is no single contiguous space that can satisfy the request, even though the total amount of free space exceeds the size of the request.

# User-level memory-allocation library - Assumptions

- `void *malloc(size_t size)`:
  - accept number of bytes requested by the application.
  - return a pointer to a region of that size (or greater).
- `void free(void *ptr)`:
  - takes a pointer and free the corresponding chunk.
- The space that this library manages is known as the `heap`. The data structure used to manage free space in the heap is some kind of **free list**.
- We are primarily concerned with **external fragmentation**.
  - If an allocator hands out chunks memory bigger than that requested, any unasked for space in such a chunk is considered **internal fragmentation**.
- Once memory is handled out to a client, it cannot be relocated to another location in memory. Thus, no **compaction** of free space is possible.
  - However, **compaction** could be used by the OS to deal with fragmentation when implementing **segmentation**.
- The allocator manages a contiguous region of bytes.
- For simplicity, assume that region has fixed size _(in reality, the allocator could ask for a region to grow)_.

# Low-level mechanisms

## Splitting and coalescing

- Splitting: Find a free chunk of memory that can satisfy the request and split it into 2. 1 chunk is returned to the caller, the other remains on the free list.
- Coalescing: When a chunk of memory is free, if it is next to 1 or 2 existing free chunk(s), merge them into a single chunk.

## Track size of allocated regions

- Keep extra information in a header block for each chunk.
- `required_size = header_size + requested_size`
- Example:

```c
typedef struct {
  int size; // size of allocated region
  int magic; // for integrity checking
} header_t;

void free(void *ptr) {
  header_t *hptr = (header_t *) ptr - 1;
  // ...
}
```

## Embedding a free list

- Build the free list inside the free space itself.
- Assume we have a 4096-byte chunk of memory to manage. Initially, the list should have 1 entry of size 4096 (minus header size).

```c
// List node
typedef struct __node_t {
  int size;
  struct __node_t *next;
} node_t;

// Initialize the heap
// . mmap() returns a pointer to a chunk of free space
size_t heap_size = 4096
node_t *head = mmap(NULL, heap_size, PROT_READ|PROT_WRITE, MAP_ANON|MAP_PRIVATE, -1, 0);
head->size = heap_size - sizeof(node_t);
header->next = NULL;
```

## Grow the heap

- Most traditional allocators start with a small-sized heap, then request more memory from OS when they run out.
- System call to request more space: `brk`, `sbrk` in UNIX systems.
- To service `sbrk` request, OS finds free physical pages and maps them into address space of the requesting process.

# Basic strategies

## Best fit

- Mechanism: Find the smallest chunk that satisfies the request.
- Intuition: Keep the large chunks for larger request.
- Cost: Performance penalty to perform an exhaustive search.

## Worst fit

- Mechanism: Find the largest chunk that satisfies the request.
- Cost: Still require a full search of free space.

## First fit

- Mechanism: Find the first chunk that satisfies the request.
- Advantage: Exhaustive search is not needed.
- Cons: Pollute the beginning of the list with tiny, unusable free segments.

## Next fit

- Mechanism: Similar to first-fit, but start searching from last location.
- Advantage: Avoid the splintering of the beginning of the list.

# Other approaches

## Segregated lists

- Idea: If an application requests a popular size, keep a separate list just to manage objects of that size. Other requests are forwarded to a more general allocator.
- Benefits of fixed-size chunks: allocation and free requests can be served quickly; no fragmentation.

## Buddy allocation

- Idea:
  - Free memory it thought of as 1 big space of size 2^N
  - When a request for memory is made, the search for free space recursively divides free space by 2 until a block that is just big enough to accommodate the request is found. The block is returned to user.
  - Cons: internal fragmentation, as we only give out power-of-2-sized blocks.
- Free a x-sized block:
  - Check if the "buddy" x-sized block is free. If so, coalesce 2 blocks into a 2x-sized block. Continue until the entire free space is restored or when a buddy not free.
- Determine the buddy:
  - The address of each buddy pair differs by a single digit, which bit is determined by the level in the buddy tree.

## Other ideas

- Advanced allocators use more complex data structures: balanced binary trees, splay trees, partially-ordered trees.
- Make allocators work well on multi-processor-based systems.
