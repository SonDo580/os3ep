# Segmentation

- Instead of having just 1 base-and-bounds pair in the MMU, have a base-and-bounds pair per logical **segment**.
- A **segment** is a contiguous portion of the address space
- The OS can then place each segment in different parts of physical memory, avoid filling physical memory with unused virtual address space.
- With 3 segments (code, heap, stack), the MMU need 3 base-and-bounds register pairs.
- Accessing an illegal address causes **segmentation fault**.

# Address translation

## Explicit approach

- Split the (virtual) address space into segments based on the top few bit of the virtual address.
- **Example**: 14-bit virtual address

```md
- Use top 2 bits to decide segment (3 segments)
  - 00: code
  - 01: heap
  - 10: (unused)
  - 11: stack
- The remaining bits are offset into the segment.
- Check validity with the segment base-and-bounds.
```

- **Pseudocode**:

```python
seg_mask = (1 << 13) & (1 << 12) # (set bit 13 and bit 12)
seg_shift = 12
offset_mask = (1 << 12) - 1 # (set bit 0 to bit 11)

segment = (virtual_addr & seg_mask) >> seg_shift
offset = virtual_addr & offset_mask
if (offset >= sizes[segment])
    raise Exception(PROTECTION_FAULT)
else
    physical_addr = base[segment] + offset
```

- **Issues**:
  - 1 segment goes unused -> some systems put code in the same segment as the heap (only need 1 bit to select segment).
  - each segment is limited to a maximum size.

## Implicit approach

- Hardware determines segment by noticing how the address was formed
  - address generated from program counter (an instruction fetch) -> code segment.
  - address is based off of stack pointer -> stack segment.
  - other addresses -> heap segment.

# Stack

- Besides base-and-bounds values, hardware also needs to know which way the segment grows:
  - code, heap: `grows_positive? = 1`
  - stack: `grows_positive? = 0`

- **Pseudocode**:

```python
seg_mask = (1 << 13) | (1 << 12) # (set bit 13 and bit 12)
seg_shift = 12
offset_mask = (1 << 12) - 1 # (set bit 0 to bit 11)
MAX_SEGMENT_SIZE = 1 << 12 # 4KiB

segment = (virtual_addr & seg_mask) >> seg_shift
offset = virtual_addr & offset_mask

if (grow_positive[segment]):
  if (offset >= sizes[segment]):
      raise Exception(PROTECTION_FAULT)
  else:
      physical_addr = base[segment] + offset
else:
  neg_offset = offset - MAX_SEGMENT_SIZE
  if abs(neg_offset) > sizes[segment]:
    raise Exception(PROTECTION_FAULT)
  physical_addr = base[segment] + neg_offset
```

# Support sharing

- Sometimes it's useful to share certain memory segments between address spaces _(**code sharing** is common)_ -> need extra hardware support in the form of **protection bit**:
  - code: read-execute
  - heap: read-write
  - stack: read-write
- Hardware algorithm update: Raise exception if user process tries to
  - write to a read-only segment
  - execute from a non-executable segment

# Fine-grained vs. Coarse-grained segmentation

- Coarse-grained: address space only has a few segments (code, stack, heap)
- Find-grained: address space has a large number of smaller segments -> require further hardware support, with a **segment table** stored in memory.

# OS support

- Save/restore segment registers to/from memory.
- Grow/shrink segment.
- Manage free space in physical memory

# Pros

- Better support **sparse** address spaces.
- Address translation is fast and well suited to hardware.
- Code sharing.

# Issues

- **External fragmentation**: physical memory becomes full of little holes of free space, making it difficult to allocate new segments or to grow existing one.
  - **Solution**:
    - **Compact** physical memory by rearranging existing segments.
    - Use a free-list management algorithm that tries to keep large extent of memory available for allocation: **best-fit**, **worst-fit**, **first-fit**, **buddy algorithm**.
- Still not flexible enough to support fully generalized, sparse address space.
  - For example, if we have a large-but-sparse heap segment, the entire heap must still reside in memory.
