- Distributed file systems:
  - The servers have the disks.
  - Clients send messages across the network to access their directories and files on those disks.
- Why need it:
  - Easy **sharing** of data across clients.
  - **Centralized administration**: For example, backing up files can be done from the few server machines, instead of from multiple clients.
  - **Security**: Have all servers in a locked machine room.

# A basic distributed file system

- Distributed file systems provide **transparent** access to files.
- Client applications issue **system calls** to the client-side file system, in order to access files and directories on the server.
- The file system looks the same as a local file system, except for performance.
- Example:
  - The client issues a `read()` request.
  - The client-side file system sends a message to the **server-side file system** (commonly called the **file server**) to read the block.
  - The file server reads the block from disk or its in-memory cache.
  - The file server sends a message back to the client.
  - The client-side file system copy the data into the user buffer supplied to `read()` -> The request completes.
  - Subsequent `read()` on the same block on the client may be **cached** in client memory or on client's disk -> No network traffic is generated.

# Sun's network file system (NFS)

- Instead of building a proprietary and closed system, Sun developed an **open protocol** which specified the message formats that clients and servers would use to communicate.

# Aside: Why servers crash

- Power outage.
- Software bugs.
- Memory leaks.
- Network is partitioned _(server is working but appear as if it has crashed)_.

# Focus: simple and fast server crash recovery

- In NFSv2, the main goal was **simple and fast server crash recovery**.
- In a multi-client, single-server environment: As the server goes, so goes the entire system.

# Key to fast recovery: Statelessness

- The server does not keep track of what is happening at each client. Each request contains all the information needed to complete it.
- Example of a **stateful** protocol: the `open()` system call.
  - Given a pathname, `open()` returns a file descriptor. The descriptor is used on subsequent `read()` or `write()` requests to access various file blocks.
  - Imagine the client-side file system opens the file by sending a message. The file server opens the file locally on its side and sends the descriptor back. On subsequent reads, the client application uses this descriptor to call `read()`.
  - The file descriptor is **shared state** (**distributed state**) between the client and the server.
  - Shared state complicates crash recovery: Imagine the server crashes after the first read completes. After the server is up and running again, the client issues the second read. But now the server has now idea to which file 'fd' is referring _(that is lost when the server crashed)_.
  - To handle this, the client and server would have to engage in a **recovery protocol**, where the client have to keep enough information in its memory to be able to tell the server what it needs to know _(in this case, that file descriptor 'fd' refers to file 'foo')_.
- Stateful server with client crashes:
  - Imagine a client opens a file then crashes. The `open()` uses up a file descriptor on the server. How can the server know it is OK to close the file?
- The designers of NFS decided to pursue a stateless approach.

# The NFSv2 protocol

- **File handle**: Uniquely describe a file or directory a particular operation is going to operate upon.
- A file handle has 3 important components:
  - a **volume identifier**: which file system
  - an **inode number**: which file within that partition
  - a **generation number**: needed when reusing an inode number. By incrementing it whenever an inode number is reused, the server ensures that a client with an old file handle can't accidentally access the newly-allocated file.
- Important components of NFSv2 protocol:
  - `LOOKUP` protocol message: used to obtain a file handle, which is subsequently used to access file data.
  - the directory file handle for the root directory of a file system is obtained through the NFS **mount protocol**.
  - attributes are metadata about each file _(the same type of information obtained through `stat()`)_.
  - One a file handle is available, the client can issue `READ` and `WRITE` protocol messages.
  - The `GETATTR` request fetches attributes for a file.

# From protocol to distributed file system

- The client-side file system tracks open files and translates application requests into protocol messages.
- The server responds to protocol messages, each contains all of the information needed.
- Example: reading a file

```
  Client                                Server
----------------------------------------------------------------------
fd = open("/foo", ...);

- Send LOOKUP(rootdir FH, "foo"),
                                        - Receive LOOKUP request.
                                        - Look for "foo" in root dir.
                                        - Return foo's FH + attributes.
- Receive LOOKUP reply.
- Allocate fd in open file table.
- Store foo's FH in table.
- Store current file offset (0).
- Return fd to app.

----------------------------------------------------------------------
read(fd, buffer, MAX);

- Index into open file table with fd
  to get FH and current file offset.
- Send READ(FH, offset=0, count=MAX).
                                        - Receive READ request.
                                        - Use FH to get volume/inode num.
                                        - Read inode from disk (or cache).
                                        - Compute block location (with offset).
                                        - Read data from disk (or cache).
                                        - Return data to client.
- Receive READ reply.
- Update file offset (+ bytes read).
  Current file position = MAX.
- Return data/error code to app.


----------------------------------------------------------------------
(Subsequent reads are similar, just with different offsets)

----------------------------------------------------------------------
close(fd);

(Don't need to talk to server)
- Cleanup local structures:
  Free descriptor fd in open file table.
```

- Notes:
  - Client tracks all relevant **state** for file access:
    - mapping of integer file descriptors to NFS file handle.
    - current file offset.
  - When the file is opened for the first time, client sends a LOOKUP request for each segment in the pathname.
  - Each request tells the server all the information it needs.

# Handle server failure with idempotent operations

- The client may not receive a reply. Reasons:
  - The message is dropped by the network -> request or reply could be lost.
  - The server has crashed.
- In NFSv2, the client simply **retries** the request after **timeout**.
- This ability is due to an important property of most NFS requests: **idempotency** _(performing the operation multiple times has the same effect as a single time)_.
  - `LOOKUP` and `READ` requests are trivially idempotent.
  - `WRITE` requests are also idempotent: the message contains data, count, and exact offset to write to.
  - ...
- Some operations are hard to make idempotent.
  - `MKDIR`: If the file server executes successfully but the reply is lost, the client may repeat it and receive an error _(directory already exists)_.

# Improve performance: Client-side caching

- The NFS client-side file system caches file data and metadata received from server in its client memory.
- The cache also servers as a temporary buffer for writes.

# The cache consistency problem

- Example: 3 clients, 1 server
  - C1 reads file F and cache it.
  - C2 overwrites file F to F[v2].
  - C3 has not accessed file F.
- Subproblem 1: **update visibility** - When do updates from 1 client become visible at other client?
  - C2 may buffer writes in its cache for a long time before propagating them to the server.
  - Other clients trying to access F will get stale version F[v1].
- Subproblem 2: **stale cache**
  - C2 finally flushes its writes to the file server. Server now has latest version F[v2].
  - C1 still has stale version F[v1] in its cache.
- Address update visibility: Clients implement **flush-on-close** (a.k.a., **close-to-open**) semantics.
  - When a file is written to and subsequently closed by a client application, the client flushes all updates _(dirty pages in the cache)_ to the server.
  - Subsequent open from another node will see the latest file version.
- Address stale-cache problem:
  - Clients check whether a file has changed before using its cached contents: Before using a cached block, the client issue a `GETATTR` request to the server to fetch the file's attribute.
  - If the time of modification is more recent, the client **invalidates** the file _(removing it from the client cache)_. Subsequent reads will go to the server and retrieve the latest version of the file.
  - If the client has the latest version of the file, it will use the cached contents.
  - A new problem: the NFS server was flooded with `GETATTR` requests.
  - **Common case**: A file was accessed only from a single client, but the client always had to send `GETATTR` requests to the server to make sure no one else had changed the file.
  - To remedy this situation, an **attribute cache** was added to each client. The attributes would timeout after a certain amount of time _(say 3 seconds)_. During that time, all file accesses would determine that it was OK to use the cached file.

# Assessing NFS cache consistency

- The flush-on-close behavior introduced a certain performance problem:
  - If a temporary or short-lived file was created on a client and then soon deleted, it would still be forced to the server.
  - A more ideal implementation will keep such short-lived files in memory until they are deleted and thus remove the server interaction entirely.
- The addition of an attribute cache made it very hard to reason about exactly what version of a file one was getting.
  - Sometimes you would get the latest version.
  - Sometimes you would get an old version because your attribute cache hadn't timed out.
- Details of an implementation can define user-observable semantics.

# Implications on server-side write buffering

- When data and metadata is read from disk, NFS servers will keep it in memory. Subsequent reads of said data will not go to disk.
- On a `WRITE`:
  - If the server returns success to the client right after placing the data into memory, it may result in incorrect behavior. The server can crash before writing it to disk.
  - To avoid that, NFS servers must commit each write to persistent storage before informing the client of success.
- Thus, write performance can be the major performance bottleneck:
  - One trick is to first put writes in a battery-backed memory, enabling quick reply to `WRITE` requests without fear of losing data and without the cost of writing to disk right away.
  - The second trick is to use a file system design specifically to write to disk quickly when one finally needs to do so.

# Aside: VFS

- NFS also required other fundamental innovations. The most lasting is the **Virtual File System (VFS) / Virtual Node (vnode)** interface.
- The VFS layer includes operations that are done to an entire file system: mounting, unmounting, getting file system statistics, forcing all dirty writes to disk, ...
- The vnode layer consists of all operations one can perform on a file: open, close, read, write, ...
- To build a new file system, one simply has to define these methods. The framework than handles the rest, connecting system calls to the particular file system implementation, performing generic function common to all file system (e.g., caching) in a centralized manner.
  -> Provide a way for multiple file system implementations to operate simultaneously within the same system.

# Key NFS terms

- Main goal of NFS: fast and simple crash recovery.
- The key to realize that goal: **stateless** protocol.
  - After a crash, the server can quickly restart and start serving requests again; clients just **retry** requests until they succeed,
- Making requests **idempotent** is a central aspect of NFS.
  - Enables client retry without worry.
- Performance concerns dictate the need for client-side **caching** and **write buffering**, but introduces **cache consistency problem**.
- NFS provide solution to cache consistency:
  - **flush-on-close** (**close-to-open**): when a file is closed, its contents are forced to the server -> other clients can then observe the updates.
  - attribute cache: reduces the frequency of checking with the server whether a file has changed _(via `GETATTR` requests)_.
- NFS server must commit writes to persistent media before returning success. Otherwise, data loss can arise.
  - Some systems use battery-backed memory.
- To support NFS integration into the operating system, Sun introduced the **VFS/vnode** interface, enabling multiple file system implementations to coexist in the same OS.
