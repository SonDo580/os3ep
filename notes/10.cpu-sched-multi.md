- Adding more CPUs does not automatically make an application run faster. You have to rewrite your application to run in **parallel**, perhaps using **threads**.
- Beyond applications, a new problem for the OS is **multiprocessor scheduling**.

# Background: Multiprocessor architecture

- In a system with a single CPU, there is a hierarchy of **hardware caches** that in general help the processor run programs faster.
- Caches are based on the notion of **locality**, of which there are 2 kinds: **temporal locality** and **spatial locality**.
- Caching with multiple CPUs is much more complicated.
- **Cache coherence** problem:
  - Imagine a program running on CPU 1 reads a data item D at address D. Since D is not on CPU 1's cache, the system fetches it from main memory.
  - The program then modifies the value at address A, just updating its cache with the new value D'. The system usually writes the data to memory later.
  - Then assume the OS stops running the program and moves it to CPU 2.
  - The program re-reads the value at address A. But there's no such data in CPU 2's cache, thus the system fetches the value from memory, and gets the old value D instead of correct value D'.
- The basic solution is provided by hardware:
  - The hardware monitors memory accesses and ensure that the view of a single shared memory is preserved.
  - 1 way to do this on a bus-based system is to use **bus snooping**:
    - Each cache pay attention to memory updates by observing the bus that connects them to main memory.
    - When a CPU sees an update for a data item it holds in its cache, it will **invalidate** its copy or **update** it.
    - Write-back caches make this more complicated, because the write to main memory isn't visible until later.

# Issue: Cache affinity

- A process, when run on a particular CPU, builds up a fair bit of state in the caches and TLB of the CPU.
- The next time the process runs, it is advantageous to run it on the same CPU, since some of its state is already present in the caches on that CPU.
- A multiprocessor scheduler should consider this when making decisions.

# Single-queue scheduling

- **Single-queue multiprocessor scheduling (SQMS)**: Put all jobs that need to be scheduled into a single queue.
- Advantage: simplicity
  - Instead of picking the best job, pick the best X jobs if there are X CPUs.
- Problem 1: Lack of **scalability**
  - The SQMS code itself runs on multiple CPUs, so we need **locking** for it to work correctly _(access a single queue to find the next jobs to run)_.
  - Locks can greatly reduce performance, as the number of CPUs in the system grows.
- Problem 2: Cache affinity.
  - Assume we have 5 jobs (A, B, C, D, E) and 4 processors.
  - Our scheduling queue looks like this:

  ```
  (Queue)->A->B->C->D->E->(NULL)
  ```

  - Assume each job runs for a time slice then another job is chosen. Here's a possible job schedule across CPUs:

  ```
  CPU 0: A E D C B ...
  CPU 1: B A E D C ...
  CPU 2: C B A E D ...
  CPU 3: D C B A E ...
  ```

  - Because each CPU simply picks the next job to run from the globally shared queue, each job ends up bouncing around from CPU to CPU _(doing exactly the opposite of what would make sense from the standpoint of cache affinity)_.
  - To handle this, one might provide affinity for some jobs, but move others around to balance load. For example, imagine the 5 jobs are scheduled as follow:

  ```
  CPU 0: A E A A A ...
  CPU 1: B B E B B ...
  CPU 2: C C C E C ...
  CPU 3: D D D D E ...
  ```

  - You could then decide to migrate a different job for the next time through, thus achieving some kind of affinity fairness.

# Multi-queue scheduling

- Some systems opt for multiple queues, 1 per CPU. This approach is called **multi-queue multiprocessor scheduling (MQMS)**.
- Each queue follow a particular discipline (e.g., round robin).
- When a job enters the system, it is placed on exactly 1 scheduling queue, according to some heuristic _(e.g., random, or picking one with fewer jobs than others)_.
- Avoid the problems of information sharing and synchronization found in the single-queue approach.
- Advantage over SQMS: More scalable:
  - As the number of CPUs grows, so too the number of queues. Lock and cache contention is not a central problem.
  - MQMS intrinsically provides cache affinity. Jobs stay on the same CPU.
- Problem: **load imbalance**. Example:
  - A and C run on CPU 0, B and D run on CPU 1.
  - C completes -> only A runs on CPU 0.
  - A completest -> CPU 0 is idle.
- Solution: **migration** - move jobs around.
  - Example: CPU 0 is idle, B and D run on CPU 1 -> move B or D to CPU 0.
  - Example: A runs on CPU 0, B and D run on CPU 1 -> continuously migrate 1 or more jobs.
  ```
  CPU 0: A A A A B A B A B B B B ...
  CPU 1: B D B D D D D D A D A D ...
  ```
- How should the system decide a migration?
- A basic approach is to use the **work stealing** technique.
  - A (source) queue that is low on jobs will occasionally peek at another (target) queue, to see how full it is.
  - If the target queue is (notably) more full, the source will "steal" 1 or more jobs from the target to help balance load.
- Problem:
  - If you look at other queues too often, you will suffer from high overhead and have trouble scaling.
  - If you don't look at other queues very often, you are in danger of suffering severe load imbalances.

# Linux multiprocessor schedulers

- Overtime, 3 different schedulers arose:
  - The O(1) scheduler.
  - The Completely Fair Scheduler (CFS).
  - The BF Scheduler (BFS).
- Both O(1) and CFS use multiple queues, while BFS uses a single queue.
- The O(1) scheduler is a priority-based scheduler, changing a process's priority over time and scheduler those with highest priority _(similar to MLFQ)_.
- CFS is a deterministic proportional-share approach _(more like Stride scheduling)_.
- BFS is also proportional-share, but based on a complicated scheme known as Earliest Eligible Virtual Deadline First (EEVDF).

# Summary

- Building a general purpose scheduler is hard. Small code changes can lead to large behavioral differences.
