- How to build systems that work when components **fail**?
- System **performance** and **security** are critical.
- The most basic aspect in distributed system: **communication**.
  - The most basic primitive: **message**.

# Communication basics

- Communication is fundamentally unreliable: packages are regularly lost or corrupted.
- Causes:
  - some bits get flipped due to electrical problem.
  - some elements _(network link, router, host)_ in the system are damaged.
  - packets are **dropped** due to lack of buffering within a network switch / router / endpoint.

# Unreliable communication layers

- Don't deal with packet loss. Let applications communicate with a basic unreliable messaging layer.
- Example: the **UDP/IP** networking stack.
- To use UDP, a process uses the **sockets** API to create a **communication endpoint**. Processes on the other machines or the same machine send UDP **datagrams** to the original process.
- UDP includes a **checksum** to detect some form of packet corruption.

# Reliable communication layers

- We need mechanisms and techniques to handle packet loss.
- How does the sender know that the receiver has actually received the message:
  - **acknowledgement** (**ack**).
- When should the sender do if it does not receive an acknowledgement:
  - **timeout** + **retry**.
  - Note: the sender must keep a copy of the message around in case it needs to send it again.
- We usually want to guarantee that each message is received **exactly once** by the receiver.
  - Problem: receiver received message and acknowledged -> the ack is lost -> sender will retry.
  - Solution: The sender has to identify each message in some unique way. When the receiver sees a duplicate transmission, it acknowledges the message but does **not** pass the message up to the application.
- To detect duplicate messages:
  - 1. **Unique ID**:
    - The sender could generate a unique ID for each message.
    - The receiver could track every ID it has ever seen.
    - This is costly, requiring unbounded memory to track all IDs.
  - 2. **Sequence counter**:
    - The sender and receiver agree upon a start value for a counter that each side will maintain.
    - When a message is sent, the current counter value N is sent along with the message _(serves as ID)_. The sender then increments the counter value to N + 1.
    - The receiver uses its counter value as the expected value for the ID of the incoming message. If the ID of the received message (N) matches the receiver's counter value (N), it acknowledges the message and passes it up to the application. The receiver then increments its counter to N + 1.
    - If the ack is lost, the sender will timeout and re-send message N. This time, the receiver's counter is higher (N + 1), so the receiver knows it has received this message. Thus it acknowledges the message but doesn't pass it up to the application.
- Example: **TCP/IP**.

# Communication Abstraction

- **Distributed shared memory (DSM)** systems:
  - Enable processes on different machines to share a large, virtual address space.
  - Work through the virtual memory system of the OS: When page is accessed, 2 things can happen:
    - The page is already on the local machine -> Data is fetched quickly
    - The page is currently on some other machine -> A page fault occurs, the page fault handler sends a message to some other machine to fetch the page, install it in the page table of the requesting process.
  - Not widely used for a number of reasons:
    - Failure handling: If a machine fails, parts of the address space become unavailable.
    - Performance: Some accesses cause expensive fetches from remote machines.

# Remote procedure call (RPC)

- While OS abstraction is a poor choice for building distributed systems, programming language abstractions make more sense.
- **Remote procedure call (RPC)**:
  - Goal: Make the process of executing code on a remote machine as simple and straightforward as calling a local function.
  - The server defines some routines that it wants to export. The rest is handled by the RPC system, which has 2 pieces: a **stub generator** (**protocol compiler**), and the **runtime library**.

## Stub generator

- Input: the set of calls a server wishes to export.
  - Example:

  ```
  interface {
    int func1(int arg1);
    int func2(int arg1, int arg2);
  };
  ```

- For the client, a **client stub** is generated. A client program would link with this client stub and call into it to make RPCs.
- To the client, the code appears as a function call. Internally, the code does this:
  - **Create a message buffer**: usually a contiguous array of bytes.
  - **Pack the needed information into the message buffer**: function identifier, arguments.
    - This step is called **marshaling** or **serialization**.
  - **Send the message to the destination RPC server**.
  - **Wait for the reply**.
  - **Unpack return code and other arguments**:
    - This step is called **unmarshaling** or **deserialization**.
  - **Return to the caller**.
- Code is also generated for the server. Steps taken:
  - **Unpack the message**: Extract function identifier and arguments.
  - **Call into the actual function**.
  - **Package the result**: Results are marshaled into a reply buffer.
  - **Send the reply** to the caller.
- Complex arguments:
  - Example: `write(int fd, char* buf, size_t size)`.
  - The RPC package needs to be able to interpret the pointer.
- Concurrent server:
  - Handling 1 request at a time is inefficient.
  - A common organization is a **thread pool**. The RPC calls may now need to use synchronization primitives.

## Runtime library

- **Naming** problem: How to locate a remote service?
  - Simplest approach: The client must know the hostname or IP address of the machine running the desired RPC service, and the port number it is using -> DNS.
- Which transport layer protocol to use?
  - We want reliability, but using TCP is too inefficient. For each request/response cycle, 2 "extra" ack messages are sent.
  - Many RPC packages are built on top of unreliable communication layers, such as UDP. The RPC layer provides reliability by using similar mechanisms like timeout/retry, acknowledgement, sequence numbering.

## Other issues

- Long-running remote call:
  - With timeout, it might appear as a failure to client.
  - One solution is to use an explicit acknowledgement _(request received)_ when the reply isn't immediately generated. After some time, the client can periodically ask whether the server has done.
- Large arguments (cannot fit in a single packet):
  - Some lower-level network protocols provide **sender-side fragmentation** and **receiver-side reassembly**. If not, the RPC runtime may have to implement itself.
- **Byte ordering**:
  - Some machines store values in **big endian** ordering, while others use **little endian** ordering.
  - RPC packages handle this by providing a well-defined endianness within their message formats.
- Asynchronous communication:
  - Typical RPCs are made **synchronously**: Client must wait for the procedure call to return before continuing.
  - Some RPC packages enable calling an RPC **asynchronously**: The RPC package sends the request and returns immediately. The client is then free to do other work. Some time later, the client calls back into the RPC layer and waits for outstanding RPCs to complete.
