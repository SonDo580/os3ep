- **Data integrity** / **data protection**: Ensure that data is safe _(what you put in is the same when the storage system returns it)_.

# Disk failure modes

- Early RAID systems use the **fail-stop** model: Either the entire disk is working, or it fails completely.
- Modern disks will occasionally seem to be mostly working but have trouble accessing 1 or more blocks.
- 2 common types of single-block failures:
  - **latent sector errors (LSEs)**.
  - **block corruption**.
- LSEs arise when a disk sector or group of sectors has been damaged:
  - a **head crash** damages the surface.
  - cosmic rays can also flip bits.
- In-disk **error correcting codes (ECC)**:
  - Are used by the drive to determine whether the on-disk bits in a block are good; and in some cases, to fix them.
  - If the drive does not have enough information to fix the error, the disk will return errors to read requests.
- A disk block can become **corrupt** in a way not detectable by the disk (**silent faults**):
  - buggy disk firmware may write a block to the wrong location -> from client's perspective, the wrong block is returned when subsequently accessed.
  - the block is transferred from the host to the disk across a faulty bus -> the corrupt data is stored by the disk.
- **Fail-partial** disk failure mode:
  - disks can still fail entirely.
  - disks can also seemingly be working and have 1 or more blocks become inaccessible (LSEs) or hold the wrong contents (corruption).
- When accessing a seemingly-working disk:
  - it may return an error (non-silent partial fault).
  - it may return the wrong data (silent partial fault).

# Handle latent sector errors

- When a storage system tries to access a block and the disk returns an error:
  - Use redundancy mechanism to return the correct data.
- Example:
  - Access the alternate copy.
  - In RAID-4/5 systems based on parity: Reconstruct the block from other blocks in the parity group.
- Problem in RAID-4/5 systems: Both full-disk faults and LSEs occur in tandem.
  - When an entire disk fails, the RAID tries to **reconstruct** the disk (onto a hot spare) by reading through all the other disks in the parity group and recomputing missing value.
  - If an LSE is encountered on any one of the disks during reconstruction, the reconstruction cannot successfully complete.
  - Some systems add an extra level of redundancy, by having 2 parity disks instead of 1. When an LSE is discovered during reconstruction, the extra parity disk helps to reconstruct the missing block.

# Detecting corruption: The checksum

- **Detecting** of corruption is a key problem.
- Once it is known that a block is bad, **recovery** is the same: You need to have some other copy around.
- **Checksum**:
  - Is the result of a function that takes a chunk of data _(say a 4KB block)_ and produces a small summary _(say 4 to 8 bytes)_.
  - Enable a system to detect if data has been corrupted or altered: Store checksum with data. Confirm upon later access that current checksum _(computed from current data)_ matches stored value.

## Common checksum functions

- Vary in strength and speed.
- XOR:
  - XOR'ing each chunk of data.
  - Reasonable.
  - If 2 bits in the same position within each unit change, the checksum will not detect the corruption.
- Addition:
  - Perform 2's-complement addition over each chunk of data.
  - Fast.
  - Not good if the data is shifted.
- **Fletcher checksum**:
  - Involves the computation of 2 check bytes: s1 and s2.
  - Assume a block D consists of bytes `d1...dn`:
    - initially: `s1 = s2 = 0`.
    - `s1 = (s1 + di) mod 255` over all di.
    - `s2 = (s2 + s1) mod 255` over all di.
  - Is almost as string as CRC.
- **Cyclic redundancy check (CRC)**:
  - Treat the data block D as a large binary number, divide it by a value k. The remainder of this division is the value of the CRC.
- There is no perfect checksum. 2 data blocks with non-identical contents may have identical checksums (a **collision**). Try to find one the minimizes the change of collision.

## Checksum layout

- Given a data block D, let's call the checksum over that data C(D).
- Without checksum:

```
|  D0  |  D1  | ...
```

- With checksum: Add a single checksum for every block.

```
| C(D0) |  D0  | C(D1) |  D1  | ...
```

- Problem:
  - Checksums are usually small (e.g., 8 bytes).
  - Disks can only write in (multiple of) sector-sized chunks (512 bytes).
- One solution is to format the drive with 520-byte sectors _(an extra 8 bytes per sector can be used to store the checksum)_.
- In disks that don't have that functionality, we can store n checksums in a sector, followed n data blocks:

```
| C(D0) . C(D1) |  D0  |  D1  | ...
```

- This works on all disks but is less efficient:
  - If the file system wants to overwrite block D1, it has to read in the checksum sector containing C(D1), update C(D1) in it, then write out both the checksum sector and the new data block D1.
  - The earlier approach _(1 checksum per sector)_ just perform a single write.

# Using checksum

- When reading a block D, the client _(file system or storage controller)_ also reads its **stored checksum** Cs(D) from disk. The client then computes the **computed checksum** Cc(D) over the retrieved block D.
- If 2 checksums are equal, the data has _likely_ not been corrupted, and thus can be safely returned to the user. If they do not match, we have a corruption.
- What should we do with a corruption:
  - If the storage system has a redundant copy, try to use it.
  - If the storage system has no such copy, return an error.

# Misdirected writes

- Data is write disk correctly, but in the wrong location.
- Solution: Add a **physical identifier (physical ID)** to each checksum.
  - The stored information now contains the checksum C(D) and both the disk and sector numbers of the block.

# Lost writes

- The device informs the upper layer that a write has completed but in fact it is never persisted.
- The old block likely has a match checksum, so the above checksumming strategies doesn't help to detect lost writes.
- 1 approach is to perform a **write verify** or **read-after-write**:
  - Immediately read back the data _(bypass the cache)_ after a write to ensure that data indeed reached the disk surface.
  - This is slow.
- Some systems add a checksum elsewhere in the system to detect lost writes.
  - Sun's ZFS includes a checksum in each inode and indirect block for every block in a file.
  - If the write to a data block is lost, the checksum within the inode will not match the old data.
  - This still fails if the writes to both the inode and the data are lost simultaneously.

# Scrubbing

- Some checking occurs when data is accessed by applications, but most data is rarely accessed and remain unchecked.
- Unchecked data is problematic for a reliable storage system, as bit rot could eventually affect all copies of a particular piece of data.
- Many systems utilize **disk scrubbing**:
  - Periodically read through every block of the system, and check whether checksums are still valid.
  - This reduces the chances that all copies of a certain data item become corrupted.
  - Typical systems schedule scans on a nightly or weekly basis.

# Overheads of checksumming

- Space: small
  - On the disk: Each stored checksum takes up room on the disk, which can no longer be used for user data.
  - In memory: When accessing data, there must be room in memory for the data and the checksums. If the system only checks the checksum then discards it once done, this overhead is short-lived.
- Time: noticeable
  - The CPU must compute the checksum over each block, both when the data is stored and when it is accessed.
  - 1 approach to reduce CPU overheads is to combine data copying and checksumming into 1 activity _(doing both tasks in a single pass)_, because the copy is need anyhow _(e.g., copy data from kernel page cache into user buffer)_.
  - Beyond CPU overheads, some checksumming schemes can induce extra I/O overheads:
    - When checksums are stored distinctly from the data -> Can be reduced by design.
    - Extra I/O needed for scrubbing -> Control when scrubbing activity takes place _(middle of the night may be a good time)_.
