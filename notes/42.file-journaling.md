- Problem: **crash-consistency**
  - How to update persistent data structures despite the presence of a **power loss** or **system crash**.
  - Example: Need multiple writes, but only a few can completes -> The on-disk structure will be left in an **inconsistent** state.
- Approaches:
  - **fsck (file system checker)**: used by older file systems.
  - **journaling (write-ahead logging)**: adds a little bit of overhead to each writes but recovers more quickly.

# A detailed example

## Assumptions

- **Workload**: append a single data block to an existing file.
  - Steps: open the file, call `lseek()` to move the file offset to the end, issue a single 4KB write, close the file.
- File system structures:
  - 1 inode bitmap: 8 bits, 1 per inode.
  - 1 data bitmap: 8 bits, 1 per data block.
  - inodes: 8 total, spread across 4 blocks.
  - data blocks: 8 total.
- To append a block, the file system must perform 3 separate writes to the disk: 1 for the inode, 1 for the data bitmap, 1 for the data block.
- If a crash happens after 1 or 2 of these writes but not all 3, the file system will be in an inconsistent state.

## Crash scenarios

- Just the data block is written to disk:
  - The data is on disk but there is no inode that points to it and the bitmap doesn't say the block is allocated.
  - It is as if the write never occurred -> not a problem from the perspective of file system crash consistency _(but a problem for users - they lose data)_.
- Just the updated inode is written to disk:
  - The inode points to the disk address of the new block, but the new block has not been written there. If we trust the pointer, we will read **garbage** data.
  - **File system inconsistency**: The on-disk bitmap says that data block has not been allocated, but the inode says that it has.
- Just the updated bitmap is written to disk:
  - The bitmap says that the block is allocated, but there is no inode that points to it.
  - The file system is inconsistent again. This would result in **space leak** if left unresolved.
- Just the inode and bitmap are written to disk:
  - The file system metadata is consistent.
  - But the data block has garbage (old) data again.
- Just the inode and the data block are written to disk:
  - The inode points to correct data on disk.
  - But we have inconsistency between the inode and the (old) bitmap.
- Just the bitmap and the data block are written to disk:
  - We have inconsistency between the (old) inode and the bitmap.
  - Even though the block was written and the bitmap indicates its usage, we have no idea which file it belongs to _(no inode points to the block)_.

## Crash consistency problem (consistent update problem)

- We want to move the file system from 1 consistent state to another **atomically**.
- But the disk only commits 1 write at a time, and crashes or power losses may occur between these updates.

# Solution 1: The file system checker (fsck)

- Let inconsistencies happen and fix them later (when rebooting).
- Unix tool: `fsck`.
- Can't fix all problems: Like the case where the file system looks consistent but the inode points to garbage data.
- Goal: Make sure the file system metadata is internally consistent.
- The tool is run before the file system is mounted and made available _(`fsck` assumes that no other file system activity is going on while it runs)_. Once finished, the on-disk file system should be consistent and thus be made accessible to users.
- Summary of what `fsck` does:
  - **Superblock**:
    - Check if the superblock looks reasonable, mostly doing sanity checks such as making sure the file system size is larger than the number of allocated blocks.
    - The goal is to find a corrupt superblock. In that case, the system administrator may decide to use an alternate copy of the superblock.
  - **Free blocks**:
    - Scan the inodes, indirect blocks, double indirect blocks, ... to build an understanding of which blocks are currently allocated within the file system.
    - It uses this knowledge to produce a correct version of the allocation bitmaps.
    - If there is inconsistency between bitmaps and inodes, it is resolved by trusting the information within the inodes.
  - **Inode state**:
    - Each inode is checked for corruption or other problems.
    - Example: Make sure each allocated inode has a valid type field (regular file, directory, symbolic link, ...).
    - If the inode cannot be easily fixed, it is cleared and the inode bitmap is updated accordingly.
  - **Inode links**:
    - Verify the link count of each allocated inode.
    - Scan through the entire directory tree, starting at the root directory, and build its own link counts for every file and directory.
    - If there is a mismatch, the count within the inode is fixed.
    - If an allocated inode is discovered but no directory entry refers to it, is is moved to the `lost+found` directory.
  - **Duplicates**:
    - Check for duplicate pointers _(2 different inodes refer to the same block)_.
    - If 1 inode is obviously bad, it must be cleared.
    - Alternatively, the pointed-to block could be copied, giving each inode its own copy.
  - **Bad blocks**:
    - A pointer is considered "bad" if it obviously points to something outside its valid range _(Example: address of the block is greater than the partition size)_.
    - In this case, just removes the pointer from the inode or indirect block.
  - **Directory checks**:
    - fsck does not understand the contents of user files. However, directories hold information created by the file system itself.
    - Perform integrity checks on the contents of each directory: '.' and '..' are the first entries, each inode referred to by a directory entry is allocated, no directory is linked to more than once in the entire hierarchy _(a directory can only have 1 parent)_.
- Problem: **too slow**.
  - With a large disk volume, scanning the entire disk to find all the allocated blocks and read the entire directory tree may take minutes or hours.
  - It is incredibly expensive to scan the entire disk to fix problems that occurred during an update of just a few blocks.

# Solution 2: Journaling (Write-ahead logging)

- Steal the idea from database management systems.
- Basic idea: When updating the disk, before the overwriting the structures in place, first write down a note _(somewhere else on the disk, in a well-known location)_ describing the intention.
- If a crash takes place during the update of the structures, you can go back and look at the note you made and try again, instead of having to scan the entire disk.
- Journaling adds a bit of work during updates to greatly reduce the amount of work required during recovery.
- Assuming the journal is placed within the same file system image _(sometimes it is placed on a separate device, or as a file within the file system)_, a **Linux ext3** file system looks like this:

```
| Super | Journal | Group 0 | Group 1 | ... | Group N |

Each group:
| inode bitmap | data bitmap | inodes | data blocks |
```

## Data journaling

- Say we wish to write the inode Iv2, bitmap Bv2, and data block Db to disk _(see the append workload above)_.
- Before writing them to their final disk locations, we now write them to a log (journal).

```
| TxB | Iv2 | Bv2 | Db | TxE | --->
```

- We have written 5 blocks:
  - The transaction begin (TxB) tells us about this update: information about the pending update (final addresses of Iv2, Bv2, Db), **transaction identifier (TID)**.
  - The middle 3 blocks contain the exact contents of the blocks. This is known as **physical logging** _(**logical logging** puts a more compact logical representation of the update in the journal, which is more complex but save space in the log and improve performance)_.
  - The final block (TxE) marks the end of this transaction, and also contains the TID.
- Once the transaction is safely on disk, we are ready to overwrite the old structures in the file system. This process is called **checkpointing** _(bringing the file system up to date with the pending update in the journal)_.
  - Issue the writes to Iv2, Bv2, Db to their disk locations.
  - If the writes complete successfully, we have successfully checkpointed the file system.
- Sequence of operations:
  - 1. **Journal write**: Write the transaction, including a transaction-begin block, all pending data and metadata updates, and a transaction-end block, to the log. Wait for these writes to complete.
  - 2. **Checkpoint**: Write the pending data and metadata updates to their final locations in the file system.
- Problem: a crash occurs during the writes to the journal.
  - 1 way is to issue each write at a time, waiting for each to complete, and then issuing the next. However, this is **slow**.
  - We'd like to issue all 5 block writes at once tp turn 5 writes into 1 single sequential write. However, this is **unsafe**.
  - The disk internally may perform scheduling and complete small pieces of the big write in any order. Thus, the disk may (1) write TxB, Iv2, Bv2, TxE and later (2) write Db. When a crash occurs between (1) and (2), this is what ends up on disk:

  ```
  | TxB | Iv2 | Bv2 | ??? | TxE | --->
  ```

- Why is this a problem:
  - The transaction looks valid _(it has a begin and an end with matching sequence numbers)_.
  - If the file system now reboots and runs recovery, it will replay this transaction and copy the contents of the garbage block to the location of Db.
- To avoid this problem, the file system issue the transactional write in 2 steps:
  - Write all blocks except TxE to the journal, issuing these writes all at once.
  - When those writes complete, the file system issues the write of the TxE block, thus leaving journal in the final, safe state.
  - Important: The disk guarantees that any 512-byte write is **atomic**. To make sure the write of TxE is atomic, we should make it a single 512-byte block.
- (Updated) Protocol to update the file system:
  - 1. **Journal write**: Write the the transaction-begin block, all pending data and metadata updates to the log. Wait for these writes to complete.
  - 2. **Journal commit**: Write the transaction commit block to the log. Wait for the write to complete. The transaction is said to be **committed**.
  - 3. **Checkpoint**: Write the pending data and metadata updates to their final on-disk locations.

## Recovery

- If the crash happens before the transaction is committed, the pending update is simply ignored.
- If the crash happens after the transaction is committed, but before the checkpoint is complete, the file system can **recover** the update as follow:
  - When the system boots, scan the log and look for transactions that have committed to the disk.
  - **Replay** these transactions in order.
  - This form of logging is called **redo logging**.
- It is fine for a crash to happen at any point during checkpointing.
  - The updates are simply performed again during recovery.
  - Because recovery is rare **(only taking place after an unexpected system crash)**, a few redundant writes are OK.

## Batching log updates

- Example: Create files in the same directory.
- To create 1 file, one has to update a number of on-disk structures: the inode bitmap (to allocate a new inode), the newly-created inode of the file, the data block of the parent directory, the parent directory inode (new modification time).
- If we commit all of this information to the journal for each file creation, some blocks will be written multiple times.
- Solution:
  - Some file systems do not commit each update to disk 1 at a time.
  - One can buffer all updates into a global transaction.

## Making the log finite

- 2 problems when the log becomes full:
  - The larger the log, the longer recovery will take, as the recovery process must replay all the transactions within the log in order.
  - No further transactions can be committed to the disk.
- Solution: Treat the log as a circular data structure, reusing it over and over _(The journal is sometimes called a **circular log**)_.
  - Once a transaction has been checkpointed, free the space it was occupying within the journal, allowing the log space to be reused.
  - 1 way: Mark the oldest and newest non-checkpointed transactions in a **journal superblock**. All other space is free.

  ```
  Journal:
  | Journal super | Tx1 | Tx2 | ... | --->
      |  |        ^           ^
      |__|________|___________|
  ```

- (Updated) Protocol:
  - 1. **Journal write**: Write the the transaction-begin block, all pending data and metadata updates to the log. Wait for these writes to complete.
  - 2. **Journal commit**: Write the transaction commit block to the log. Wait for the write to complete. The transaction is said to be **committed**.
  - 3. **Checkpoint**: Write the pending data and metadata updates to their final on-disk locations.
  - 4. **Free**: Some time later, mark the transaction free in the journal by updating the journal superblock.
- Problem: We are writing each data block to the disk twice.

## Metadata journaling

- Problem:
  - Write traffic is doubled.
  - Between writes to the journal and writes to the main file system, there is a costly seek.
- The mode of journaling described above is called **data journaling**.
- A simpler and more common form of journaling is called **ordered journaling** (or **metadata journaling**).
- The following information would be written to the journal _(assuming the earlier workload)_:

```
| TxB | Iv2 | Bv2 | TxE | --->
```

- The data block would instead be written to the file system, avoiding the extra write. Since most I/O traffic is data, not writing data twice substantially reduces the I/O load.
- When should we write data blocks to disk:
  - If we write Db to disk after the transaction containing Iv2 and Bv2 completes, the file system is consistent but Iv2 may end up pointing to garbage data.
  - To ensure that a pointer will never point to garbage, write data blocks _(of regular files)_ to the disk first, then write related metadata.
- (Updated) protocol:
  - 1. **Data write**: Write data to final location. (Optionally) wait for completion.
  - 2. **Journal metadata write**: Write the transaction-begin block and metadata to the log. Wait for completion.
  - 3. **Journal commit**: Write the transaction-commit block to the log. Wait for completion. The transaction (including data) is now **committed**.
  - 4. **Checkpoint metadata**: Write the contents of the metadata update to their final locations on disk.
  - 5. **Free**: Later, mark the transaction free in journal superblock.
- Note: It's fine to perform steps 1 and 2 concurrently. The only requirement is that steps 1 and 2 complete before step 3.
- General rule: "write the pointed-to object before the object that points to it".

## Tricky case: Block reuse

- Suppose you are using metadata journaling _(data blocks are not journaled)_.
- Let say you have a directory called 'foo'. The user adds an entry to 'foo' _(say by creating a file)_, and the contents of foo are written to the log _(include the data block since directories are considered metadata)_:

```
| TxB  | I[foo]    | D[foo]     | TxE  |
| id=1 | ptr: 1000 | addr: 1000 | id=1 |
```

- The user deletes everything in 'foo' and 'foo' itself, freeing up block 1000 for reuse.
- The user creates a new file ('bar'), which ends up reusing block 1000 that used to belongs to 'foo'. The inode of 'bar' is committed to the journal, the newly-written data in block 1000 is not _(since we are using metadata journaling)_.

```
| TxB  | I[foo]    | D[foo]     | TxE  | TxB  | I[bar]    | TxE  |
| id=1 | ptr: 1000 | addr: 1000 | id=1 | id=2 | ptr: 1000 | id=2 |
```

- Assume a crash occurs and all of this information is still in the log. During replay, the recovery process will replay everything in the log, including the write of the directory data in block 1000. The relay thus overwrites the user data of current file 'bar' with old directory contents.
- Solution 1: Never reuse blocks until the delete of said blocks is checkpointed out of the journal.
- Solution 2: Add a new type of record to the journal, known as a **revoke** record.
  - Deleting the directory would cause a revoke record to be written to the journal.
  - When replaying the journal, the system first scans for revoke records. Any revoked data is never replayed.

# Solution 3: Other approaches

- **Soft Updates**:
  - Carefully order all writes to the file system to ensure that on-disk structures are never left in an inconsistent state.
  - Example: write pointed-to data block to disk before the inode that points to it -> ensure that the inode never points to garbage.
  - Requires intricate knowledge of each file system data structure -> adds a fair amount of complexity to the system.
- **Copy on write (COW)**:
  - Never overwrite files or directories in place.
  - Place new updates to unused locations on disk.
  - After a number of updates are completed, flip the root structure of the file system to include pointers to the newly updated structures.
- **Backpointer-based consistency (BBC)**:
  - No ordering is enforced between writes.
  - An additional **back pointer** is added to every block in the system _(e.g., each data block has a reference to the inode in which it belongs)_.
  - When accessing a file, the file system can determine if the file is consistent by checking if the forward pointer _(e.g., the address in the inode's direct pointer)_ points to a block that refers back to it.
- **Optimistic crash consistency**:
  - Goal: Reduce the number of times a journal protocol has to wait for disk writes to complete.
  - How: Issue as many writes to disk as possible by using a generalized form of the **transaction checksum**, and include a few other techniques to detect inconsistencies should they arise.
  - Require a slightly different disk interface to function well.
