- A different style of concurrent programming: **event-based concurrency**.
- Popular usage: NodeJS, Nginx, Redis, ...

# Basic idea: an event loop

- Idea: Wait for an event to occur. When it does, check what type of event it is and do the small amount of work it requires (issuing I/O requests, scheduling other events, ...).
- Pseudocode for event loop:

```c
while (1) {
    events = getEvents();
    for (e in events)
        processEvent(e);
}
```

- The code that processes each event is known as an **event handler**.
- Deciding which event to handle next is equivalent to scheduling.
- How can the server know if an event has occurred?

# Important API: `select()` (or `poll()`)

- Example: A network application can check whether any network packets have arrived in order to service them.
- `select()`: see man page.

```c
int select(
    int nfds,
    fd_set *restrict readfds,
    fd_set *restrict writefds,
    fd_set *restrict errorfds,
    struct timeval *restrict timeout
);
```

- Lets us check whether descriptors can be read from _(new packets has arrived and need processing)_ or written to _(it is OK to reply, the outbound queue is not full)_.
- Timeout: can be set to NULL, which cause `select()` to block indefinitely, until some descriptors are ready.
- `poll()`: similar, see man page.

# Using `select()`

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <sys/types.h>
#include <unistd.h>

int main(void) {
    // open and setup sockets
    // ...

    // main loop
    while (1) {
        fd_set readFDs;
        FD_ZERO(&readFDs); // clear (set all bits to 0)

        // set the bits for the descriptors the server is interested in
        // (for simplicity, all min->max)
        int fd;
        for (fd = minFD; fd < maxFD; fd++) {
            FD_SET(fd, &readFDs);
        }

        // do the select
        int rc = select(maxFD+1, &readFDs, NULL, NULL, NULL);

        // check which actually have data and process them
        int fd;
        for (fd = minFD; fd < maxFD; fd++) {
            if (FD_ISSET(fd, &readFDs))
                processFD(fd);
        }
    }
}
```

- A real server is more complicated: sending messages, issuing disk I/O, ...

# Why simpler? No locks needed

- Because only 1 event is being handled at a time, there's no need for locks.
- An event-based server cannot be interrupted by another thread because it is single threaded.

# Problem: Blocking system calls

- Example:
  - Client requests server to read a file from disk and return its content.
  - The event handler will need to issue an `open()` system call to open the file, followed by a series of `read()` calls to read the file.
  - Both calls issue I/O requests to the storage system, thus may take a long time to service.
- With a thread-based server, this is no issue:
  - While the thread issuing the I/O request suspends (waiting for the I/O to complete), other threads can run, enabling the server to make progress.
- With an event-based approach:
  - There are no other threads to run, just the main event loop.
  - If an event handler issues a call that blocks, the entire server will block until the call completes.
- A rule in event-based systems: no blocking calls are allowed.

# Solution: Asynchronous I/O

- Many modern operating systems introduced asynchronous I/O.
- These interfaces enable an application to issue an I/O request and return control immediately to the caller, before the I/O has completed.
- Additional interfaces enable an application to determine whether the I/O has completed.

## Example: interface on Mac

- The APIs revolve around a basic structure - the asynchronous I/O control block (**AIO control block**):

```c
// Simplified
struct aiocb {
    int aio_fildes; // file descriptor
    off_t aio_offset; // file offset
    volatile void *aio_buf; // location of buffer
    size_t aio_nbytes; // length of transfer
}
```

- To issue an asynchronous read to a file, an application must fill the structure with relevant information: the file descriptor of the file to be read, the offset within the file, the length of the request, the target memory location to copy read results.
- After the structure is filled in, the application must issue the asynchronous call to read the file, using the **asynchronous read** API: `int aio_read(struct aiocb *aiocbp);`
  - This call tries to issue the I/O. If successful, it returns right away and the application can continue.
- How can we tell when an I/O is complete? Use `aio_error()` API on Mac: `int aio_error(const struct aiocb *aiocbp);`
  - This call checks whether the request referred to by `aiocbp` has completed. If it has, the routine returns success (0). If not, `EINPROGRESS` is returned.
  - An application can use it to periodically **poll** the system.

## Other systems

- Some systems provide an approach based on **interrupt**. This method uses UNIX **signals** to inform applications when an asynchronous I/O completes, thus removing the need for polling.
  - This **polling vs. interrupt** is seen in I/O devices too.

# Problem: State management

- Event-based code is generally more complicated to write than thread-based code.
- Reason: **manual stack management**
  - When an event handler issues an asynchronous I/O, it must package up some program state for the next event handler to use when the I/O finally completes.
  - This additional work is not needed in thread-based programs, as the state the program needs is on the stack of the thread.

# Other difficulties

- In modern systems with multiple CPUs, the server has to run multiple event handlers in parallel to utilize more than 1 CPU.
  -> The usual synchronization problems arise.
- Does not integrate well with certain kinds of system activities, such as **paging**. If an event handler page faults, it will block, and the server will not make progress until the page fault completes.
  -> The server is structured to avoid **explicit blocking**, but **implicit blocking** is hard to avoid.
- Event-based code is hard to manage over time. For example, if a routine changes from non-blocking to blocking, the event handler that calls that routine must also change, by ripping itself into 2 pieces.
  -> Programmers must always be on the lookout for such API changes.
- Asynchronous disk I/O does not integrate with asynchronous network I/O in a simple and uniform manner.
