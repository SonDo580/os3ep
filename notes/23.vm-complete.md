# Lazy optimization

## Demand zeroing

- When a page is added to an address space, the OS puts an entry in the page table that marks the page inaccessible.
- When the process reads or writes the page, it will trap into the OS. The OS will find a physical page, zero it, and map it into the process's address space.
- Why zeroing: required for security; otherwise processes can read content leaved by other processes.

## Copy on write

- When the OS needs to copy a page from 1 address to another, instead of copying it, it maps it into the target address space and marks it read-only in both address spaces.
- If both processes only read the page, no further action is taken.
- If 1 process try to write to the page, it will trap into the OS. The OS will allocate a new page, fill it with the data, and map this new page into the address space of the faulting process.
- Example: `fork()` and `exec()`
  - `fork()` creates an exact copy of the address space of the caller. With a large address space, making a copy is slow.
  - Most of the address space is immediately overwritten by the subsequent call to `exec()`, which overlays the calling process's address space with that of the to-be-executed program.

# Page cache (in Linux)

- To reduce costs from accessing persistent storage.
- Keep pages from 3 primary sources:
  - **memory-mapped files**.
  - file data and metadata from devices.
  - heap and stack pages that comprise each process (**anonymous memory**, no named file underneath but **swap space**).
- These entities are kept in a **page cache hash table**.
- The page cache check if entries are **clean** or **dirty**.
- Dirty data is periodically written to the backing store by background threads (called `fdflush`). This takes place after a certain time period or if too many pages are dirty (both configurable parameters).
