- **vsfs (Very Simple File System)**:
  - A simplified version of a typical Unix file system.
  - Introduce basic on-disk structures, access methods, policies.

# The way to think

- **Data structures**:
  - To organize data and metadata.
  - Simple structures: array of blocks or other objects.
  - Complicated structures: tree-based.
- **Access methods**:
  - Which structures are read / written during the execution of a particular system call (open, read, write)? How efficiently are these steps performed?

# Overall organization

- Divide the disk into **blocks**:
  - Simple file systems use just 1 block size. Let's choose 4KB.
  - The blocks are addressed from 0 to N-1.
  - Assume we have a really small disk with just 64 blocks.
- The region of the disk used for user data is the **data region**.
  - For simplicity, reserve a fixed portion of the disk: the last 56 blocks.
- The file system has to track information about each file. This information is the **metadata**.
  - Track things like: which data blocks comprise the file, file size, owner and access rights, access and modify time, ...
  - Usually use a structure called an **inode**.
  - The portion of the disk reserved for inodes is the **inode table**, which holds an array of on-disk inodes: use 5 blocks (3 -> 7).
  - Assume 256 bytes per inode, a 4KB block can hold 16 inodes, and our file system contains 80 inodes _(maximum number of files we can have)_.
- We also need some way to track whether inodes or data blocks are free or allocated (**allocation structures**):
  - We could use a **free list** that points to the first free block, which then points to the next free block, and so forth.
  - We instead choose a simple structure called **bitmap**, 1 for the data region (the **data bitmap**), 1 for the inode table (the **inode bitmap**): use 2 blocks (1 and 2).
  - Each bit in the bitmap is used to indicate whether the corresponding block is free (0) or in-use (1).
- Block 0 is reserved for the **superblock**:
  - Contains information about the file system: how many inodes and data blocks are in the system (80 and 56), where the inode table begins (block 3),...
  - Include a magic number to identify the file system type (**vsfs** in this case).
- When mounting a file system, the OS will read the superblock first to initialize various parameters, and attach the volume to the file system tree. When files within the volume are accessed, the system will know where to look for the needed on-disk structures.

# File organization: The inode

- The name **inode** is short for **index node**. The name reflects the fact that these nodes were originally stored in an array, which the system indexed into to access.
- Each inode is referred to by a number (the **i-number**), which is called the **low-level name** of the file. Given an i-number, we can calculate where on disk the corresponding inode is located.
- Example: Read inode number 32

```c
block = (i_number * sizeof(inode_t)) / block_size;
sector = (inode_start_addr + (block * block_size)) / sector_size;

/*
. i_number = 32
. sizeof(inode_t) = 256B
. block_size = 4KB
. inode_start_addr = 12KB (after super block, inode bitmap, data bitmap)
. sector_size = 512B
*/
```

- Inside each inode is information about a file: type (regular file, directory, ...), size, number of blocks allocated to it, protection information (who owns the file, who can access it), time information (created / modified / last accessed), where the data blocks reside on disk (pointers).
- How inode refers to where data blocks are:
  - Simple approach: Use **direct pointers** (disk addresses). Each pointer refers to 1 disk block that belongs to the file.
  - Limitation: If you have a really big file, bigger than the block size multiplied with the number of direct pointers in the inode.

## Multi-level index

- To support bigger file, have a special pointer known as an **indirect pointer**. Instead of pointing to a block that contains user data, it points to a block that contains more pointers, each of which points to user data.
- An inode may have a fixed number of direct pointers and a single indirect pointer. If a file grows large enough, an indirect block is allocated (from the data block region of the disk), and the indirect pointer is set to point to it.
  - Assuming 4KB blocks and 4B disk addresses, that adds another 1024 pointers. The file can grow an additional `1024 * 4KB = 4MB`.
- To support even bigger files, add another pointer: the **double indirect pointer**. This pointer refers to a block that contains pointers to indirect blocks, each of which contain pointers to data blocks.
  - The file can grow an additional `1024 * 1024 * 4KB = 4GB`.
- Still want more? Add the **triple indirect pointer**.
- This imbalanced tree is referred to as the **multi-level index** approach to pointing to file blocks.
- Why use an imbalanced tree: Most files are small. With a small number of direct pointers (typically 12), an inode can directly point to 48KB of data.

## Extents

- A different approach is to use **extents** instead of pointers.
- An extent is a disk pointer plus a length (in blocks).
- A single extent is limiting _(hard to find a contiguous chunk of on-disk free space when allocating a file)_. Thus, extent-based file systems often allow for more than 1 extent.
- Pointer-based approaches are flexible but use a large amount of metadata per file.
- Extent-based approaches are less flexible but more compact. They work well when there is enough free space on disk and files can be laid out contiguously _(which is the goal for virtually any file allocation policy)_.

## Linked-list based

- Inside an inode, instead of having multiple pointers, you just need one to point to the 1st block of the file.
- To handle larger file, add another pointer at the end of that data block, and so on.
- Perform poorly for some workloads:
  - Reading the last block of a file.
  - Doing random access.
- To make linked allocation work better, some systems keep an in-memory table of link information:
  - The table is indexed by the address of a data block D.
  - The content of an entry is D's next pointer (address of the next block).
  - A NULL value indicates end-of-file. Some other marker indicates that the block is free.
- The above is the basic structure of the **FAT (file allocation table)** file system.

# Directory organization

- A directory contains a list of (entry name, inode number) pairs for files and directory in it. For each string, there may also be a length. Those entries are saved in data blocks of the directory.
- Example:
  - Each entry has an inode number, record length (the total bytes for the name plus leftover space), string length (the actual length of the name), and the name of the entry.
  - Each record has 2 extra entries: '.' and '..'
- Deleting a file (`unlink()`) can leave an empty space in the middle of the directory.
  - There's should be a way to mark that _(e.g., with a reserved inode number like 0)_.
  - The delete is 1 reason the record length is used: A new entry may reuse an old, bigger entry.
- Where directories are stored:
  - File systems treat directories as a special type of file.
  - A directory has an inode and data blocks pointed to by the inode _(and perhaps indirect blocks)_.
- Beside the simple linear list of directory entries above, some file systems store directories in B-tree form, making file create operations _(which have to ensure that a file name has not been used)_ faster than systems with simple lists that must be scanned in entirety.

# Free space management

- There are many ways to manage free space:
  - Bitmaps
  - Free lists: A single pointer in the super block points to the first free block. Inside that block the next free pointer was kept, and so on. When a block was needed, the head block was used.
  - B-tree.
- In vsfs, we use 2 simple bitmaps.
- Example: Create a file
  - Search through the bitmap for a free inode and allocate it to the file. - Update the on-disk bitmap to mark the inode as used.
  - Allocating a data block is similar.
- Other considerations when allocating data blocks:
  - Some Linux file systems will look for a sequence of free blocks -> Guarantees that a portion of the file will be contiguous on the disk, thus improving performance.
  - Such **pre-allocation** policy is a commonly-used heuristic when allocating space for data blocks.

# Access paths: Reading and Writing

- For the following examples, assume that the file system has been mounted and the superblock is already in memory. Everything else is still on the disk.

## Reading a file from disk

- Assume we want to open the file '/foo/bar', read it, then close it. Assume the file is 12KB in size (3 blocks).
- `open("/foo/bar", O_RDONLY)`: The file system must **traverse** the path name and locate the desired inode for the file 'bar'.
- Traversals begin at the root of the file system, in the **root directory** (/).
  - The FS must read in the block that contains the inode of the root directory.
  - The root has no parent so its inode number must be known in advance. In most Unix file systems, the root inode number is 2.
- The FS look inside the inode to find pointers to data blocks, which contains the contents of the root directory. After reading in a few data blocks, the FS will find the entry for 'foo' with the inode number (say it is 44).
- The next step is to recursively traverse the pathname until the desired inode is found. The FS reads the block containing the inode of 'foo' and then its directory data, finally finding the inode number of 'bar'.
- The final step is to read the inode of 'bar' into memory. The FS then does a final permissions check, allocates a file descriptor in the per-process open file table, and returns it to the user.
- Once open, the program can issue `read()` system calls.
  - The first read (at offset 0 unless `lseek()` was used) will read the first block of the file, consulting the inode to find the location of that block. It may also update the inode with a new last accessed time.
  - The read will further update the in-memory open file table for this file descriptor: Update the file offset so the next read will read the second block, ...
- At some point, the file will be closed. The file descriptor would be deallocated.

### Reading a file from disk - summary

- The open causes numerous reads in order to locate the inode of the file.
- Afterwards, reading each block requires the file system to consult the inode, read the block, then update the inode's last-accessed-time field with a write.
- The amount of I/O generated by the open is proportional to the length of the pathname.
  - For each additional directory, we have to read its inode and its data.
  - With a large directory, we might have to read many data blocks to find the desired entry.

## Writing a file to disk

- First, the file must be opened (as above). Then the application can issue `write()` calls to update the file with new contents. Finally, the file is closed.
- Writing to the file may also **allocate** a block _(unless the block is being overwritten)_.
  - Each write logically generates 5 I/Os: 2 to read and write the data bitmap _(allocate a free block, mark the block as used)_. 2 more to read and write the inode _(which is updated with the new block location)_. 1 to write the actual block itself.
- The amount of traffic is worse for file creation:
  - To create a file, the file system must allocate an inode, and also allocate space within the directory containing the new file.
  - I/O traffic: 1 read to the inode bitmap _(to find a free inode)_, 1 write to the inode bitmap _(to mark allocated inode)_, 1 write to the new inode itself _(to initialize it)_, 1 write to the data of the directory _(to link the high-level name of the file to its inode number)_, 1 write to the directory inode to update it.
  - If the directory needs to grow to accommodate the new entry, additional I/Os _(to the data bitmap and the new directory block)_ will be needed.

# Caching and Buffering

## Caching

- Most file systems aggressively use system memory (DRAM) to cache important blocks.
- Without caching, every file open would require at least 2 reads for every level in the directory hierarchy _(1 to read the inode of the directory, at least 1 to read its data)_.
- Early file systems introduced a **fixed-size cache** to hold popular blocks.
  - Use strategies like **LRU** to decide which block to keep in cache.
  - The cache would usually be allocated at boot time to be roughly 10% of total memory.
  - This **static partitioning** of memory can be wasteful.
- Modern systems employ a **dynamic partitioning** approach.
  - Integrate virtual memory pages and file system pages into a **unified page cache**.
- With caching, the first file open may generate a lot of I/O traffic, but subsequent file opens of that same file or files in the same directory will mostly hit the cache, thus no I/O is needed.

## Buffering

- Write traffic has to go to disk to become persistent.
- **Write buffering** has a number of benefits:
  - The file system can **batch** some updates into a smaller set of I/Os _(Example: an inode bitmap is updated when 1 file is created, then updated moment later as another file is created)_.
  - The system can **schedule** subsequent I/Os and thus increase performance.
  - Some writes are avoided altogether by delaying them _(Example: An application creates a file and then deletes it)_.
- Modern file systems buffer write in memory for between 5 and 30 seconds.
- Tradeoff: If the system crashes before the updates have been propagated to disk, the updates are lost.
- Some applications _(such as databases)_ don't enjoy this tradeoff.
  - To avoid data loss due to write buffering, they force writes to disk by calling `fsync()`, using **direct I/O** interfaces that work around the cache, using **raw disk** interface and avoiding the file system altogether.
