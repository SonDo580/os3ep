- **Solid-state storage**:
  - Have no mechanical moving parts like hard drives.
  - Built out of transistors _(like memory and processors)_.
  - Retain information despite power loss.
- Technology: **flash** (**NAND-based flash**)
  - To written to a given chunk of it (a **flash page**), you first have to erase a big chunk (a **flash block**), which can be quite expensive.
  - Writing too often to a page will cause it to **wear out**.

# Storing a single bit

- The level of charge trapped within the transistors is mapped to a binary value.
- In a **single-level cell (SLC)** flash, only a single bit is stored within a transistor (1 or 0).
- With a **multi-level cell (MLC)** flash, 2 bits are encoded into different levels of charge.
- There is even **triple-level (TLC)** flash, which encodes 3 bits per cell.
- Overall, SLC chips achieve higher performance and are more expensive.

# Banks / Planes

- Flash chips are organized into **banks** or **planes** which consist of a large number of cells.
- A bank is accessed in 2 different sized units:
  - **blocks (erase blocks)**: are typically of size 128KB or 256KB.
  - **pages**: are a few KB in size (e.g., 4KB).
- Within each bank there are a large number of blocks. Within each block there are a large number of pages.

# Basic flash operations

- The **read** command is used to read a page, **erase** and **program** are used in tandem to write.
- **Read (a page)**:
  - Specify the read command and the page number.
  - Quite fast _(10s of microseconds)_, regardless of the location on the device, and (more or less) regardless of the location of the previous request (unlike a disk).
  - The device is a **random access** device.
- **Erase (a block)**:
  - Before writing to a page, you must erase the entire block the page lies within.
  - Erase destroys the contents of the block (by setting each bit to value 1). Therefore, data in the block must be copied elsewhere (to memory, or to another flash block) before executing the erase.
  - The erase command is quite expensive _(milliseconds)_.
  - Once finished, the entire block is reset and each page is ready to be programmed.
- **Program (a page)**:
  - Once a block has been erased, use the program command to change some of the 1's within a page to 0's _(to write the desired content)_.
  - Less expensive than erasing a block, but more costly than reading a page _(100s of microseconds)_.
- Think that each page has a state associated with it:
  - Pages start in an INVALID state.
  - Erasing the block set the state of all pages in it to ERASED, making them programmable.
  - When you program a page, its state changes to VALID.
  - Reads do no affect these state _(although you should only read from pages that have been programmed)_.
  - Once a page has been programmed, you must erase the entire block to change its contents.
- Example: State transition within a 4-page block _(Note that program() also set new contents of the page, but it doesn't show here)_

```
            IIII    initial: pages are invalid
Erase()     EEEE    state of pages set to erased
Program(0)  VEEE    program page 0; state set to valid
Program(0)  error   cannot reprogram page after programming
program(1)  VVEE    program page 1
Erase()     EEEE    erased; all pages programmable
```

## Summary

- Reading a page: just read the page.
- Writing a page:
  - Move data we care about to another location.
  - Erase the entire block.
  - Program the desired page.
- Frequent repetitions of this program/erase cycle can lead to the biggest reliability problem: **wear out**.

# Flash performance and reliability

- Mechanical disks can fail for a variety of reasons:
  - **head crash**: the drive head makes contact with the recording surface
  - ...
- The primary concern of flash chip is **wear out**: When a flash block is erased and programmed, it slowly accrues a little bit of extra charge. Overtime, in becomes increasingly difficult to differentiate between a 0 and a 1. When it becomes impossible, the block becomes unusable.
- Another reliability problem with flash chip is **disturbance**: When accessing a particular page within a flash, some bits may get flipped in neighboring pages. Such bit flips are known as **read disturbs** or **program disturbs**.

# From raw flash to flash-based SSDs

- Flash-based SSD provides the standard block interface _(blocks/sectors of size 512 bytes or larger can be read or written given a block address)_ atop the raw flash chips.
- An SSD contains:
  - Some number of flash chips for persistent storage.
  - Some amount of volatile memory (e.g,. SRAM) for caching and buffering data, and for mapping tables.
  - Control logic to orchestrate device operation.
- Essential function of the control logic: Turn client read and write requests into internal flash operations.
  - The **flash translation later (FTL)** provides this.
  - The FTL takes read and write requests on logical blocks _(that comprise the device interface)_ and turn them into read, erase, program commands on the underlying physical blocks and physical pages.
  - Goal: excellent performance and high reliability.
- Achieve excellent performance:
  - Utilize multiple flash chips in **parallel**.
  - Reduce **write amplification**, which is defined as the total write traffic (in bytes) issued to the flash chip by the FTL divided by the total write traffic (in bytes) issued by the client to the SSD.
- Achieve high reliability:
  - **Wear leveling**: Try to spread writes across the blocks of the flash as evenly as possible, ensuring that all of the blocks wear out at roughly the same time.
  - Minimize program disturbance: Program pages within an erased block in order, from low page to high page.

# FTL organization: A bad approach

- The simplest organization of the FTL is called **direct mapped**:
  - A read to logical page N is mapped directly to a read of physical page N.
  - A write to logical page N: the FTL reads in the entire block that page N is in, erases the block, then programs the old pages as well as the new ones.
- Performance problem:
  - Severe write amplification _(proportional to the number of pages in a block)_ and as a result, terrible write performance _(slower than typical hard drives)_.
- Reliability problem:
  - Give too much control over wear out to the client workload: If file system metadata or user file data is repeatedly overwritten, the same block is erased and programmed over and over, rapidly wearing it out and potentially losing data.

# A log-structured FTL

- Most FTLs today are **log structured**.
- Upon a write to logical block N, the device appends the write to the next free spot in the currently-being-written-to block. This style of writing is called **logging**.
- To allow for subsequent reads of block N, the device keeps a **mapping table** _(in its memory, and persistent)_ that stores the physical address of each logical block in the system.
- The log-based approach:
  - Improves performance: Erases only being required once in a file.
  - Greatly enhances reliability: Spread writes across all pages, performing **wear leveling** and increase the lifetime of the device.
- Downsides:
  - Overwrites of logical blocks lead to **garbage**. The device has to periodically perform **garbage collection (GC)**. Excessive garbage collection drives up write amplification and lower performance.
  - The high cost of the mapping tables. The larger the device, the more memory needed for the table.

# FTL mapping information persistence

- What happens if the device loses power?
- The simplest thing to do is to record some mapping information with each page, in an **out-of-band (OOB)** area. When the device loses power and is restarted, it must reconstruct the mapping table by scanning the OOB areas and reconstructing the mapping table in memory.
  - Problem: Scanning a large SSD to find all mapping information is slow.
- Some higher-end devices use more complex **logging** and **checkpointing** techniques to speed up recovery.

# Garbage collection

- Basic process:
  - Find a block that contains 1 or more garbage pages.
  - Read in the live pages from that block.
  - Write out those live pages to the log.
  - Reclaim the entire block for use: Erase the block.
- To determine where each page is live or dead:
  - In each block, store information about which logical blocks are stored within each page.
  - Then use the mapping table to determine.
- Garbage collection can be expensive, requiring reading and rewriting of live data.
  - The ideal candidate is a block that consists of only dead pages. In this case, the block can immediately be erased and used for new data, without expensive data migration.
- To reduce GC cost, some SSDs **over-provision** the device.
  - By adding extra flash capacity, cleaning can be delayed and pushed to the **background** _(perhaps done at a time when the device is less busy)_.
  - Adding more capacity also increases internal bandwidth, which can be used for cleaning and thus not harm perceived bandwidth to the client.

# New storage API: `trim`

- With hard drives, we usually think of the most basic interface to read and write them:
  - read and write.
  - some kind of **cache flush** command: ensures that writes have actually been persisted.
- With log-structured SSDs _(and any device that keeps a flexible and changing mapping of logical-to-physical blocks)_, a new interface is useful: **trim**.
- The trim operation takes an address and possibly a length and informs the device that the specified blocks have been deleted.
  - The SSD can then remove the information from the FTL and later reclaim the physical space during garbage collection.

# Mapping table size

- **Page-level** mapping is impractical
- Example: With a 1TB SSD, a 4B entry per 4KB page results in 1GB (`(1TB / 4KB) * 4B`) of memory just for the mapping.

## Block-based mapping

- Only keep a pointer per block of the device, instead of per page, reducing the amount of mapping information by a factor of `size_block / size_page`.
- Does not work well for performance reasons:
  - When a small write occurs _(one that is less than the size of a physical block)_, the FLT must read a large amount of live data from the old block and copy it into a new one _(along with the data from the small write)_. This copying increases write amplification greatly and decreases performance.
- Example:
  - Think of the logical address space of the device as being chopped into chunks that are the size of the physical blocks.
  - Assume that 4 logical blocks fit within 1 chunk -> The offset portion of the logical address requires 2 bit. The remaining MSBs form the chunk number.
  - Logical blocks 2000, 2001, 2002, 2003 all have the same chunk number 500, with offsets 0, 1, 2, 3.
  - Mapping: Chunk 500 maps to block 1 (starting at physical page 4).
- Reading in block-based FTL:
  - Extract the chunk number from the logical block address (take the topmost bits).
  - Lookup the chunk-number-to-physical-page mapping in the mapping table.
  - Compute the address of the desired flash page by adding the offset from the logical address to the physical block address.

## Hybrid mapping

- The FTL keeps a few blocks erased and directs all writes to them. These are called **log blocks**.
- The FTL wants to be able to write any page to any location within the log blocks without all the copying required by block-based mapping.
  -> Keep per-page mapping for the log blocks.
- The FTL thus has 2 types of mappings in its memory:
  - **log table**: a small set of per-page mappings.
  - **data table**: the large set of per-block mappings.
- When looking for a particular logical block:
  - First consult the log table.
  - If not found, consult the data table.
- To keep the number of log blocks small, the FTL periodically examines log blocks _(which have a pointer per page)_ and switch them into blocks that can be pointed to by a single block pointer.

## 3 techniques for the switch

### Best case: **switch merge**

- Let's say the FTL has written out logical pages 1000, 1001, 1002, 1003 (all in chunk 250) and placed them in physical block 2 (physical pages 8, 9, 10, 11).
  - Log table: (empty)
  - Data table: 250 -> 8
- Now assume that the client overwrites each of these blocks in the exact same order, in 1 of the currently available log blocks, say physical block 0 (physical page 0, 1, 2, 3).
  - Log table: 1000 -> 0, 1001 -> 1, 1002 -> 2, 1003 -> 3
  - Data table: 250 -> 8
- Now the FTL can perform a **switch merge**:
  - The log block (0) now becomes the storage location for the logical blocks, and is pointed to by a single pointer.
  - The old block (2) is now erased and used as a log block.
  - Log table: (empty)
  - Data table: 250 -> 0

### Partial merge

- Imagine we have the same initial condition, but the client only overwrites logical blocks 1000 and 1001.
  - Log table: 1000 -> 0, 1001 -> 1
  - Data table: 250 -> 8
- To reunite the other pages and thus be able to refer to them by a single block pointer, FTL performs a **partial merge**:
  - Logical blocks 1002 and 1003 are read from physical block 2, then appended to the log.
  - The resulting state is the same as switch merge. But in this case, the FTL has to perform extra I/O, thus increasing write amplification.

### Full merge

- Requires even more work: The FTL must pull together pages from many other blocks to perform cleaning.
- Imagine that logical blocks 0, 4, 8, 12 are written to log block A.
- To switch this log block into block-mapped blocks:
  - The FTL must first create a data block containing logical blocks 0, 1, 2, 3, and thus must read 1, 2, 3 from elsewhere and write out 0, 1, 2, 3 together.
  - Next the merge must do the same for logical block 4, 8, 12.
  - Finally the log block A can be freed.
- Frequent full merges can seriously harm performance and thus should be avoided when at all possible.

## Page mapping plus caching

- Simplest way to reduce memory load of page-mapped FTLs: Cache only the active parts of the FTL in memory.
- If the workload only accesses a small set of pages, the translations of those pages will be stored in the in-memory FTL, and performance will be excellent.
- If memory cannot contain the **working set** of necessary translations:
  - Each access will require an extra flash read to bring in the missing mapping.
  - To make room for the new mapping, the FTL might also have to **evict** an old mapping. If that mapping is **dirty**, an extra write will also be incurred.
- In many cases, the workload will display locality, and this caching approach will both reduce memory overheads and keep performance high.

# Wear leveling

- Idea: Because multiple erase / program cycles will wear out a flash block, the FTL should try to spread the work across all blocks of the device evenly. Then all blocks will wear out at roughly the same time.
- The basic log-structuring approach does a good initial job of spreading out write load, and garbage collection helps as well.
- However, sometimes a block will be filled with long-lived data that does not get overwritten. In this case, garbage collection will never reclaim the block, and thus it does not receive its fair share of the write load.
- To remedy this problem, the FTL must periodically read all the live data out of such blocks and rewrite it elsewhere, making the block available for writing again. This increases the write amplification of the SSD, thus decreases performance.

# SSD performance and cost

## Performance

- Random I/O performance of SSDs is much better than of hard drives.
- Sequential I/O performance of SSDs is better than hard drives, but there is much less difference.
- For SSDs, random read performance is not as good as random write performance.
  - This is due to the log-structured design of many SSDs, which transforms random writes into sequential ones.
- For SSDs, the magnitude of difference between sequential and random I/Os is small.
  - But there is enough of a gap. One should still consider how to design the file systems to reduce random I/O.

## Cost

- Cost per unit of capacity of SSDs is much greater than of hard drives.
- Large data centers:
  - Often use hard drives, due to the large cost difference and the need to store massive amount of information.
  - Can also use a hybrid approach: Use a smaller number of SSDs for more popular data, while storing the less used data on hard drives to save on cost.

# Key terms

- A **flash chip** consists of many banks/planes, each of which is organized into **erased blocks**. Each block is further divided into some number of **pages**.
- Blocks are large (128KB to 2MB) and contain many pages, which are relatively small (1KB to 8KB).
- To read from a flash, issue a read command with an address and length. This allows a client to read 1 or more pages.
- Writing flash is more complex. The client must **erase** the entire block, then **program** each page exactly once.
- A new **trim** operation is useful to tell the device when a particular block / range of blocks is no longer needed.
- Flash reliability is mostly determined by **wear out**. If a block is erased too often, it will become unusable.
- A flash-based **solid-state storage device (SSD)** behaves as if it were a normal block-based read/write disk. By using a **flash translation layer (FTL)**, it transforms reads and writes from a client into reads, erases, and programs to underlying flash chips.
- Most FTLs are **log-structured**, which reduces the cost of writing by minimizing erase/program cycles. An in-memory translation layer tracks where logical writes were located within the physical medium.
- 1 key problem with log-structured FTLs is the cost of **garbage collection**, which leads to **write amplification**.
- Another problem is the size of the mapping table, which can become quite large. Using a **hybrid mapping** or just **caching** hot pieces of the FTL are possible remedies.
- One last problem is **wear leveling**. The FTL must occasionally migrate data from blocks that are mostly read in order to ensure those blocks also receive their share of the write load.
