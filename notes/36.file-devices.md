# System architecture

## Classical diagram

- The CPU attached to the main memory via some kind of **memory bus** or interconnect.
- Some devices are connected to the system via a general **I/O bus** (like **PCI**): graphics and some other higher-performance I/O devices.
- Lower down are 1 or more of **peripheral bus** (like **SCSI**, **SATA**, **USB**). These connect slow devices to the system: **disks**, **mice**, **keyboards**.

## Why do we need a hierarchical structure?

- The faster the bus is, the shorter it must be; thus a high-performance bus doesn't have much room to plug devices into it.
- Engineering a high-performance bus is costly.

## Intel's Z270 Chipset diagram

- The CPU connects most closely to the memory system, and also has a high-performance connection to the graphics card.
- The CPU connects to an I/O chip via Intel's proprietary **DMI (Direct Media Interface)**.
- The rest of the devices connect to the I/O chip via a number of different interconnects.
  - 1 or more hard drives connect to the system via the **eSATA** interface.
  - a number of **USB (Universal Serial Bus)** connections are used for low performance devices (like mice, keyboards).
  - other higher performance devices (like network interface) can be connected to the system via **PCIe (Peripheral Component Interconnect Express)**.

# A canonical device

- A device has 2 important components:
  - The hardware **interface**.
  - The **internal structure**:
    - Very simple devices have 1 or a few hardware chips.
    - More complex devices include a simple CPU, some general purpose memory, and other device-specific chips.
    - Example: Modern RAID controller might consist of hundreds of thousands of lines of **firmware**.

# The canonical protocol

- The simplified device interface is comprised of 3 registers:
  - **status** register: can be read to see the current state of the device.
  - **command** register: to tell the device to perform certain task.
  - **data** register: to pass data to the device, or get data from the device.
- Protocol:

```c
while (STATUS == BUSY)
    ; // wait until the device is not busy

// write data to DATA register

// write command to COMMAND register

while (STATUS == BUSY)
    ; // wait until the device is done with the request
```

- 4 steps:
  - The OS waits until the device is ready to receive a command by repeatedly reading the status register (**polling** the device).
  - The OS sends some data down to the data register. If this were a disk, multiple writes would need to take place to transfer a disk block to the device. When the main CPU is involved in data movement, it is called **programmed I/O (PIO)**.
  - The OS writes a command to the command register, implicitly letting the device know that data is present and it should begin working on the command.
  - The OS waits for the device to finish by polling. It may then get an error code to indicate success or failure.
- Pros: simple and working.
- Cons:
  - Polling is inefficient: It wastes CPU time just waiting for the potentially slow device to complete its activity, instead of switching to another ready process.

# Lowering CPU overhead with interrupts

- Flow:
  - Instead of polling the device repeatedly, the OS can issue a request, put the calling process to sleep, and context switch to another task.
  - When the device is finished with the operation, it will raise a hardware interrupt, causing the CPU to jump into the OS at an **interrupt handler**.
  - The handler is a piece of OS code that will finish the request _(for example, by reading data and an error code from the device)_ and wake the process waiting for I/O.
- Interrupts thus allow for **overlap** of computation and I/O.
- Using interrupts is not always the best solution.
  - If the device performs the task quickly, it's better to poll.
  - If the speed of the device is not known, use a **hybrid** approach _(poll for a little while then use interrupt if the device is not yet finished)_.
- Another reason not to use interrupts - networks:
  - When a huge stream of incoming packets each generate an interrupt, it is possible for the OS to **livelock** _(only process interrupts)_.
  - For example: For a web server, it is better to occasionally use polling to better control the system and allow the web server to service some requests before going back to check for more packet arrivals.
- Another interrupt-based optimization is **coalescing**:
  - A device which needs to raise an interrupt waits for a bit before delivering the interrupt to the CPU.
  - While waiting, other requests may complete, and thus multiple interrupts can be coalesced into a single interrupt delivery.
  - Waiting too long will increase the latency of the request.

# More efficient data movement with DMA (Direct Memory Access)

- With PIO (programmed I/O), the CPU spends too much time moving data to and from device _(before/after the I/O on the device happen)_.
- The solution is **DMA (Direct Memory Access)**. A DMA engine is a device that can orchestrate transfers between devices and main memory without CPU intervention.
- How it works:
  - To transfer data to the device, the OS would program the DMA engine by telling it where the data lives in memory, how much data to copy, which device to send it to.
  - The OS can then proceed with other work.
  - When the DMA is complete, the DMA controller raises an interrupt, and the OS thus knows the transfer is complete.

# Methods of device interaction

- The first method is to have **explicit I/O instructions**:
  - These instructions specify a way for the OS to send data to specific device registers.
  - Example: On x86, the `in` and `out` instructions can be used to communicate with devices.
  - The instructions are usually privileged. Only the OS can communicate directly with the devices.
- The second method is known as **memory-mapped I/O**:
  - The hardware makes device registers available as if they were memory locations.
  - To access a register, the OS issues a load or store the address. The hardware then routes the load / store to the device instead of main memory.

# Fitting into the OS: The device driver

- Problem: How to keep most of the OS device-neutral?
- Solution (**abstraction**): A piece of software in the OS must know in details how a device work. This is called a **device driver**.
- Example: Linux file system
  - A file system simply issues block read and write requests to the generic block layer, which routes them to the appropriate device driver, which handles the details of the specific request.
  - There's also a **raw interface** to devices, which enables special applications (**file system checker**, **disk defragmentation** tool) to directly read and write blocks without using the file abstraction.
- Downside:
  - If a device has many special capabilities, but has to present a generic interface to the rest of the kernel, those special capabilities will go unused.
