# Intro

- Memory pressure forces the OS to start paging out pages to make room for actively-used pages.
- Decide which pages to evict -> **replacement policy**.

# Cache management

- Average memory access time: `AMAT = T_m + P_miss * T_d`

```
T_m: cost of accessing memory
T_d: cost of accessing disk
P_miss (0.0 -> 1.0): probability of not finding data in the memory (cache miss)
```

- The cost of disk access is so high that even a tiny miss rate will quickly dominate the overall AMAT.
- **Cold-start miss** or **compulsory miss**: the cache begins in an empty state so the first accesses are always misses.
- Cache hit rate: `hits / (hits + misses)`
  - We can also compute hit rate ignoring the compulsory misses.

# Optimal replacement policy

- Evict the page that will be accessed furthest in the future.
- Pros: Leads to fewest number of misses overall.
- Cons: Hard to implement (we do not know the future).

# Simple policy: FIFO

- Pages are placed in a queue when they enter the system. Evict the page on the head of the queue (first-in) when replacement occurs.
- Pros: Easy to implement.
- Cons: Don't determine importance of blocks.

# Simple policy: Random

- Pages are kick out randomly when replacement occurs.
- Pros: Easy to implement.
- Cons: Don't determine importance of blocks.

# Using history: Least Frequently Used (LFU) / Least Recently Used (LRU)

- Decide which page to evict by **frequency** / **recency** of access.
- Based on the **principal of locality**: program tends to access certain code sequences and data structures frequently -> keep pages for those in memory.
- The opposite of these algorithms exist: Most Frequently Used (MFU) / Most Recently Used (MRU) -> do not work well in most cases (not all).

# Example workloads

## No locality in workload

- LRU, FIFO, Random all perform the same, with hit rate determined by cache size.
- When the cache is large enough to fit the entire workload, all policies converge to 100% hit rate.

## With locality

- Detail: hot pages are referred to most of the time.
- LRU does better than FIFO and Random since it is more likely to hold the hot pages in memory.

## Looping sequential

- Detail: Refer to 50 pages from 0 to 49, then repeat.
- Worst case for both LRU and FIFO:
  - They kick out older pages. Due to looping, these older pages are going to be accessed sooner than they pages that the policies keep in cache.
  - Even with a cache size of 49, a looping-sequential workload of 50 pages results in 0% hit rate.
  - The hit rate jump to 100% when cache size >= 50.
- Random does better in this case -> nice property: not having weird corner-case behaviors.

# Implement LRU

- Upon each page access (each memory access - instruction fetch or load/store), we must update some data structure to move this page to the most-recently-used side of the list.
  - Contrast to FIFO: the list of pages is only accessed when a page is evicted (first-in page) or added.
- 1 **method**: with hardware support
  - On each page access, the machine updates a time field in memory (in the per-process page table, or some separate array in memory with 1 entry per physical page of the system) to current time.
  - When replacing a page, the OS will scan all the time fields in the system to find the least recently used page.
- **Problem**: Scanning a huge array of times just to find the absolute LRU page is too expensive.

# Approximating LRU

- Require hardware support, in the form of a **use bit** (or **reference bit**)
- There is 1 use bit per page of the system, and the use bits live in memory (in the per-process page tables or in an array somewhere).
- When a page is referenced (read or written), the use bit is set by hardware to 1.
- The OS periodically clears the used bits (set to 0) and find pages with use bit = 0 to evict.

## Clock algorithm

- Imagine all pages of the system arranged in a circular list.
- A clock hand points to a particular page to begin with.
- When a replacement occurs, the OS check the use bit of the currently pointed to page P.
- If use bit = 1, P was recently used and thus is not a good candidate for replacement. The use bit for P is set to 0 and the clock handle is incremented to the next page.
- The algorithm continues until it finds a page with use bit = 0. This means:
  - Case 1: This page has not been used recently.
  - Case 2 (worst): All pages have been used recently, we've searched through all pages, clearing all the use bits.

# Consider dirty pages

- 1 modification to the clock algorithm: Consider whether a page has been modified or not while in memory.
  - If a page has been modified (**dirty**), it must be written back to disk to evict it, which is expensive.
  - If a page has not been modified (**clean**), the eviction is free. The physical frame can be reused for other purposes without additional I/O.
- To support this behavior, the hardware should include a modified bit (**dirty bit**). This is set any time a page is written.
- Clock algorithm's modification: Scan for pages that are both unused and clean to evict first, then pages that are unused and dirty.

# Other VM policies

## Page selection: When to bring a page into memory

- Demand paging: The OS brings the page into memory when it is accessed (on demand).
- Prefetching: The OS guesses which pages are about to be accessed and bring it in ahead of time.
  - Example: Some systems assume that if a code page P is brought into memory, code page P+1 will likely soon be accessed and thus should be brought into memory too.

## How OS writes pages out to disk

- Simple: 1 page at a time.
- More common: **clustering** / **grouping** of writes.
  - Collect a number of pending writes together in memory and write them to disk in 1 write.
  - This is more efficient because of nature of disk drives (seeking and rotational overhead).

# Thrashing

- If memory demands of the set of running processes exceed the available memory, the system will constantly be paging (swapping pages from/to disk). This condition is call **thrashing**.

## Solutions

- A system could decide not to run a subset of processes, with the hope that the remaining processes's working set (the pages that they're using actively) fit in memory and thus can make progress.
- Some current system (e.g., some versions of Linux) run an **out-of-memory killer** when memory is oversubscribed. This daemon chooses a memory-intensive process and kills it.
