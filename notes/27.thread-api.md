# Thread creation/completion

- Create thread: `pthread_create`.
- Wait for thread completion: `pthread_join`.

## Notes

- Create thread with no arguments -> pass `NULL`.
- Don't care about the return value -> pass `NULL`.
- Pass a single value -> don't have to package arguments.
- **Never** return a pointer which refers to something allocated on the thread's call stack _(it will be deallocated when the thread returns)_.
- Not all code that is multi-threaded uses the join routine. For example:
  - A multi-threaded web server might create a number of worker threads in advance (thread pool), then use main thread to accept requests and pass them to worker threads -> don't need to join.
  - A parallel program that creates threads to execute tasks will likely use join to make sure all such work completes before exiting or moving on to the next stage.

# Locks

- Provide mutual exclusion to a critical section via **locks**: `pthread_mutex_lock`, `pthread_mutex_unlock`

```c
pthread_mutex_t lock;
pthread_mutex_lock(&lock);
// ... critical section
pthread_mutex_unlock(&lock);
```

- The code above is broken:
  - lack proper initialization.
  - don't check error codes when calling lock and unlock.

- Initialize locks:

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
// OR
int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0);
```

- Done with the lock -> call `pthread_mutex_destroy`.
- Check error code:
  - Minimally: use wrappers which assert that the routine succeeded.
  - More sophisticated program: check for failure and do appropriate things.

```c
// Example wrapper
void Pthread_mutex_lock(pthread_mutex_t *mutex) {
    int rc = pthread_mutex_lock(mutex);
    assert(rc == 0);
}
```

- Sometimes avoiding getting stuck in a lock acquisition can be useful:
  - `pthread_mutex_trylock`: returns failure if the lock is already held.
  - `pthread_mutex_timedlock`: returns failure after a timeout.

# Condition variables

- Useful when some kind of signaling must take place between threads, if 1 thread is waiting for another to do something before it can continue.

## 2 primary routines

- `pthread_cond_wait(cond, mutex)`:
  - puts the calling thread to sleep, waits for some other thread to signal it.
- `pthread_cond_signal(cond)`:
  - wakes up at least 1 (typically exactly 1) thread waiting on the condition.

## Typical usage

```c
// === T1: check and sleep ===
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t lock = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
    Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);

// === T2: wakes T1 up ===
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);
```

## Notes

- We need a lock that is associated with the condition. When calling either routines, this lock should be held to prevent race condition.
- `pthread_cond_wait`:
  - releases the lock when putting the thread to sleep -> so other threads can acquire the lock and signal it to wake up.
  - reacquires the lock before returning after being woken -> ensure the thread is not interrupted between checking predicate and going to sleep.
- Why the wait call needs lock: prevent **lost signal** problem.
  - Without lock: The thread check the predicate, decide to sleep and be interrupted right before it goes to sleep. Another thread sends a signal during that period -> The signal is lost -> The 1st thread may sleep forever.
- Why the signal call needs lock:
  - Enable **wait morphing** optimization: The kernel directly moves T1 from the condition variable's wait queue to the mutex's lock queue without waking up the CPU.
- Why the wait call check the condition in a while loop, instead of a simple if statement:
  - Some `pthread` implementations can spuriously wake up a waiting thread.
  - In such cases, without rechecking, the waiting thread will think that the condition has changed even though it has not.
- Why use condition variable instead of a simple flag (`while (ready == 0)`):
