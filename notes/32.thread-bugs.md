# Types of concurrency bugs

- non-deadlock.
- deadlock.

# Non-deadlock bugs

## Atomicity violation

- A sequence of instructions that should have been executed together was not.
- Example: MySQL

```c
// Thread 1
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}

// Thread 2
thd->proc_info = NULL;
```

- Problem: If thread 1 is interrupted before the call to `fputs`, thread 2 would run in between, setting the pointer to `NULL`. When thread 1 resumes, it will crash.
- The code has **atomicity assumption** about the check for non-NULL of `proc_info` and the usage of `proc_info` in the `fputs` call.
- Fix: add a lock

```c
pthread_mutex_t proc_info_lock = PTHREAD_MUTEX_INITIALIZER;

// Thread 1
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
pthread_mutex_unlock(&proc_info_lock);

// Thread 2
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```

## Order violation

- The needed order between 2 threads was not enforced.

```c
// thread 1
void init() {
    mThread = PR_CreateThread(mMain, ...);
}

// thread 2
void mMain(...) {
    mState = mThread->State;
}
```

- Problem: Code in thread 2 assumes that `mThread` has already been initialized.
- Fix: use condition variable

```c
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t mtCond = PTHREAD_COND_INITIALIZER;
int mtInit = 0;

// thread 1
void init() {
    mThread = PR_CreateThread(mMain, ...);

    // Signal that the mThread has been created
    pthread_mutex_lock(&mtLock);
    mtInit = 1;
    pthread_cond_signal(&mtCond);
    pthread_mutex_unlock(&mtLock);
}

// thread 2
void mMain(...) {
    // Wait for mThread to be initialized
    pthread_mutex_lock(&mtLock);
    while (mtInit == 0)
        pthread_cond_wait(&mtCond, &mtLock);
    pthread_mutex_unlock(&mtLock);

    mState = mThread->State;
}
```

# Deadlock bugs

- Example:
  - Thread 1 is holding lock L1 and waiting for lock L2.
  - Thread 2 is holding lock L2 and waiting for lock L1.

```c
// Thread 1:
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);

// Thread 2:
pthread_mutex_lock(L2);
pthread_mutex_lock(L1);
```

- When this code runs, deadlock does not necessarily occur _(1 thread acquires both locks before the other thread runs)_.
- Fix: make both threads grab the locks in the same order.

## Why do deadlocks occur

1. In large code bases, complex dependencies arise between components.
2. Due to nature of **encapsulation**.

```java
Vector v1, v2;
v1.AddAll(v2);
```

- The method needs to be multi-thread safe, so locks for both vectors need to be acquired. The method acquires said locks in some arbitrary order (say v1 then v2).
- If some other thread call `v2.AddAll(v1)` at nearly the same time, we have the potential for deadlock, in a way that is quite hidden from the application

## Conditions for deadlocks

**_Need all 4 conditions_**:

- **Mutual exclusion**: Threads claim exclusive control of resources that they require (locks).
- **Hold and wait**: Threads hold resource allocated to them (acquired locks) while waiting for addition resources (locks to acquire).
- **No preemption**: Resources (locks) cannot be forcibly removed from threads that are holding them.
- **Circular wait**: There exists a circular chain of threads such that each thread hold 1 or more resources (locks) that are being requested by the next thread in the chain.

## Prevention

### Circular wait

- Provide a **total ordering** of lock acquisition: always acquire locks in a certain order.
- In more complex system, there may be many locks, thus total ordering ma be difficult to achieve (and unnecessary). A **partial ordering** can be useful.
  - Example: `A` before `B`, `B` before `C` before `D` before `E`.
- Notes:
  - Ordering is just a convention, a sloppy programmer can ignore the protocol and potentially cause deadlock.
  - Lock ordering requires a deep understanding of the code base.

### Hold and wait

- Acquire all locks at once, atomically: add a global lock.

```c
pthread_mutex_lock(prevention); // begin acquisition
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
// ...
pthread_mutex_unlock(prevention); // end
```

- Problems:
  - Encapsulation works against us: When calling a routine, this approach requires us to know exactly which locks must be held and to acquire them ahead of time.
  - Decrease concurrency: All locks must be acquired early on at once, instead of when they are truly needed.

### No preemption

- Many thread libraries provide a more flexible set of interfaces. Specifically, `pthread_mutex_trylock()` either grabs the lock if it is available and returns success, or returns error indicating the lock is held.
- A deadlock-free, ordering-robust lock acquisition protocol:

```c
top:
    pthread_mutex_lock(L1);
    if (pthread_mutex_trylock(L2) != 0) {
        pthread_mutex_unlock(L1);
        goto top;
    }
```

- Another thread could follow the same protocol but grab the locks in the other order, and the program would still be deadlock-free.
- Problem: **livelock**
  - 2 threads could both be repeatedly attempting this sequence and repeatedly failing to acquire both locks.
  - Solution: add a random delay before looping back -> decrease the chance of repeated interference among competing threads.
- Problem: **jumping back is complex**
  - If the code has acquire multiple resources along the way, it must make sure to release them as well.
- The approach doesn't really add **preemption** _(forcibly taking a lock away from a thread that owns it)_, but rather uses `trylock` to allow backing out of lock ownership _(preempt their own ownership)_.

### Mutual exclusion

- Avoid the need for mutual exclusion at all. Design **lock-free** data structures using powerful hardware instructions.
- Example 1: atomic increment with `compare-and-swap` instruction

```c
int CompareAndSwap(int *address, int expected, int new) {
    if (*address == expected) {
        *address = new;
        return 1; // success
    }
    return 0; // failure
}

void AtomicIncrement(int *value, int amount) {
    do {
        int old = *value;
    } while (CompareAndSwap(value, old, old + amount));
}
```

- Example 2: list insertion

```c
// Buggy: no locks
void insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    assert(n != NULL);
    n->value = value;
    n->next = head;
    head = n;
}

// With locks
void insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    assert(n != NULL);
    n->value = value;

    pthread_mutex_lock(listlock);
    n->next = head;
    head = n;
    pthread_mutex_unlock(listlock);
}

// Use compare-and-swap instruction
void insert(int value) {
    node_t *n = malloc(sizeof(node_t));
    assert(n != NULL);
    n->value = value;

    do {
        n->next = head;
        // retry if some other thread successfully swapped in a new head
    } while (CompareAndSwap(&head, n->next, n) == 0);
}
```

## Deadlock avoidance via scheduling

- Avoidance requires some global knowledge of which locks various threads might grab during their execution, and schedules said threads such that no deadlock can occur.
- Not a widely-used general-purpose solution:
  - Only useful in very limited environments.
  - Can limit concurrency.

### Example: 2 processors, 4 threads

- Example 1: T1 grabs L1 and L2, T2 grabs L1 and L2, T3 grabs just L2, T4 grabs no locks.
  - As long as T1 and T2 are not run at the same time, no deadlock could arise -> T1 and T2 should be run on the same processor.
- Example 2: T1 grabs L1 and L2, T2 grabs L1 and L2, T3 grabs L1 and L2, T4 grabs no locks.
  - T1, T2, T3 are all run on the same processor -> Performance cost.

## Detect and recover

- Allow deadlocks to occasionally occur, and take action when a deadlock is detected.
- Many database systems employ deadlock detection and recovery techniques:
  - A deadlock detector runs periodically, building resource graph and checking it for cycles.
  - In the event of a cycles (deadlock), the system needs to be restarted.
  - If more intricate repair of data structures is required, a human may be involved to ease the process.

# Summary

- Non-deadlock bugs:
  - Are common but often are easier to fix.
  - Include atomicity violation and order violation.
- Deadlock:
  - The best solution in practice is to be careful, develop a lock acquisition order, and thus prevent deadlock from occurring.
  - Wait-free approaches also have promises, but they lack generality and are complex to develop.
- Locks are problematic. Avoid using them unless you must.
- Develop new concurrent programming models:
  - In systems like MapReduce from Google, programmers can describe certain types of parallel computations without any locks.
