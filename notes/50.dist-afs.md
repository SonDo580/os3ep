- The Andrew File System (AFS) was introduced by Carnegie-Mellon University.
- Main goal: **scale**.
  - How a server can support as many clients as possible?
- Reasonable user-visible behavior was a first-class concern.
  - In AFS, cache consistency is simple: when the file is opened, a client will generally receive the latest consistent copy from the server.

# AFS version 1 (the ITC distributed file system)

- 1 basic tenet of all versions: **whole-file caching** on the **local disk** of the client machine that is accessing the file.
  - When you `open()` a file, the entire file is fetched from the server and stored in a file on your disk.
  - Subsequent `read()` and `write()` operations are redirected to the local file system -> require no network communication -> fast.
  - Upon `close()`, the file _(if it has been modified)_ is flushed back to the server.
- Contrasts with NFS:
  - NFS caches blocks, not whole files.
  - NFS does it in client memory, not local disk.
- More detail:
  - Client application calls `open()`.
  - The AFS client-side code (**Venus**) sends a `Fetch` protocol message to the server, passing the entire pathname of the desired file.
  - The file server (**Vice**) traverses the pathname, find the desired file, and ship the entire file back.
  - The client-side code caches the file on the local disk of the client.
  - Subsequent `read()` as `write()` act like calls to local file system. AFS also uses client memory to cache copies of blocks.
  - When finished, the AFS client checks if the file has been modified. If so, it flushes the new version back to the server with a `Store` protocol message, sending the entire file and pathname.
  - The next time the file is accessed, the client-side code contacts the server (using the `TestAuth` protocol message) to determine whether the file has changed. If not, the client uses the locally cached copy.

# Problem with version 1

- **Path traversal costs are too high**:
  - To access a file, the server must perform a full pathname traversal.
  - With many clients accessing the server at once, the server spends much of its CPU time walking directory path.
- **The client issues too many TestAuth protocol message**:
  - To check whether a local file was valid.
  - Most of the time, the file has not changed.
- Load was not balanced across servers:
  - Solution: By introducing **volumes**, which administrators could move across servers to balance load.
- The server used a single distinct process per client:
  - Induce context switching and other overheads.
  - Solution: Use threads instead of processes.

# Improving the protocol

- Each server could only service about 20 clients.

# AFS version 2 (AFS)

- Introduce the notion of a **callback** to reduce the number of client/server interactions.
  - A callback is a promise from the server to the client that the server will inform the client when a file that the client is caching has been modified.
  - By introducing this **state**, the client no longer needs to contact the server to find out if a cached file is still valid.
  - Analogy: **polling** vs. **interrupts**
- Introduce the notion of a **file identifier (FID)** _(similar to NFS **file handle**)_ instead of pathname to specify a file.
  - An FID consists of a volume identifier, a file identifier, and a "uniquifier" _(to enable reuse of the volume and file IDs when a file is deleted)_.
  - Instead of letting the server walking the pathname, the client would walk the pathname one piece at a time and cache the results.
- Example: accessing the file "/home/notes.txt".
  - Client Fetch the directory contents of "home", cache them in local disk, and setup a callback on "home".
  - Client Fetch "notes.txt", cache it in local disk, setup a callback, and return a file descriptor to the calling application.
- In the common case where a file is cached at the client, AFS behaves nearly identical to a local file system.

# Cache consistency

- Between different machines, AFS makes updates visible at the server and invalidates cached copies at the exact same time, which is when the updated file is closed.
  - The break is accomplished by contacting each client and informing it that the callback it has on the file is no longer valid.
- Between processes on the same machine, writes to a file are immediately visible to other local processes.
- When processes on different machines modify a file at the same time, AFS employs the **last writer win** approach.
  - Whichever client calls `close()` last will update the entire file on the server last and be the winner.
  - In NFS, writes of individual blocks may be flushed out by each client, thus the final file could be a mix of updates from both clients.

# Crash recovery

- Example: The server cannot contact a client to invalidate a file, while the client is rebooting.
  - When the client is up and running again, it should treat all of its cached content as suspect.
  - Upon the next access to a file, the client should first ask the server _(with a `TestAuth` protocol message)_ whether its cached copy is still valid.
- Server crash recovery is more complicated:
  - Callbacks are kept in memory. When a server reboots, it has no idea which client machine has which files.
  - We must ensure that all clients are aware of the cache in a timely manner.
    - Have the server send a "don't trust your contents" message to each client when it is up and running again.
    - OR have the clients check that the server is alive periodically _(with a **heartbeat** message)_.

# Scale and performance

- Each server could support about 50 clients.
- Client-side performance came quite close to local performance.
  - File reads usually went to the local disk cache (and local memory).
- **Assumptions**:
  - Access time: `L_net > L_disk > L_memory`.
  - First access to a file does not hit any caches. Subsequent file accesses will hit in caches.

## Observations: AFS vs. NFS

- When first reading a file, the time to fetch the file from the remote server dominates, and is similar on both systems.
  - You might think AFS would be slower, as it has to write the file to local disk. However, those writes are buffered by the local file system cache and the costs are hidden.
  - You might think that AFS reads from the local cached copy would be slower, since AFS stored the cached copy on disk. But reads on AFS would likely hit the client-side memory cache.
- Large-file sequential re-read:
  - Because AFS has a large local disk cache, it will access the file from there.
  - NFS can only cache blocks in client memory. If a large file is re-read, the client will have to re-fetch the entire file from the remote server.
  - AFS is faster then NFS by a factor of `L_net / L_disk`.
  - NFS also increases server load.
- Sequential writes perform similarly on both systems.
  - AFS writes to local cached copy and forces writes to server when the file is closed.
  - NFS buffers writes in memory, forcing some blocks to the server due to client-side memory pressure, and forces writes to server when the file is closed.
  - You might think AFS would be slower, since it writes to local disk. However, it is writing to a local file system. Those writes are first committed to the page cache, and only later to disk in the background.
- AFS performs worst on a sequential file overwrite.
  - The client first fetches the old file in its entirety, only to subsequently overwrite it.
  - NFS simply overwrite blocks and avoid the initial (useless) read.
- Workloads that access a small subset of data within large files:
  - NFS perform much better than AFS.
  - AFS fetches the entire file. Only a small read or write is performed. If the file is modified, the entire file is written back to the server.
  - NFS, as a block-based protocol, performs I/O that is proportional to the size of the read or write.

# AFS: Other improvements

- Provide a true global namespace to clients, ensuring all file were named the same way on all client machines.
  - NFS allows each client to mount NFS servers in any way that they please. Thus only by convention (and great administration effort) would files be named similarly across clients.
- Incorporate mechanisms to authenticate users and ensure that a set of files could be kept private if a user desired.
  - NFS has quite primitive support for security for many years.
- Include facilities for flexible user-managed access control _(user has control over who can access which files)_.
  - NFS has much less support for this type of sharing.
- Add tools to enable simpler management of servers for administrators.
