- We can use semaphores as both locks and condition variables.

# Definition

- A semaphore is an object with an integer value that we can manipulate with 2 routines - `sem_wait` (P) and `sem_post` (V).
- The initial value of the semaphore determines its behavior -> must initialize before using.

```c
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, 1);
// 3rd arg -> initialize value to 1
// 2nd arg = 0 -> the semaphore is shared between threads in the same process
```

- `sem_wait` and `sem_post`:
  - `sem_wait` returns right away if s's value >= 1. Otherwise the caller will be queued waiting to be woken.
  - `sem_post` does not wait for any condition.
  - When s's value < 0, the value represents the number of waiting threads.

```c
int sem_wait(sem_t *s) {
    // decrement value of s
    // wait if value of s is negative
}

int sem_post(sem_t *s) {
    // increment value of s
    // if there are threads waiting, wake one
}
```

# Binary semaphores (locks)

```c
sem_t m;
sem_init(&m, 0, 1); // initial value = 1

sem_wait(&m);
// critical section
sem_post(&m);
```

- 1st case: T0 acquires then releases the lock before T1 tries to acquire the lock.
- 2nd case: T1 tries to acquire the lock before T0 releases the lock.

# Semaphores for ordering

- Pattern:
  - 1 thread waits for something to happen
  - another thread makes that something happen, then signals that it has happened, thus waking the waiting thread.
- We can use semaphore as an **ordering** primitive (similar to the use of **condition variables**).

## Example: a parent waiting for its child

```c
sem_t s;

void *child(void *arg) {
    printf("child\n");
    sem_post(&s); // signal: child is done
    return NULL;
}

int main() {
    sem_init(&s, 0, 0); // initialize to 0
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL);
    sem_wait(&s); // wait for child
    printf("parent: end\n");
    return 0;
}
```

- 1st case: parent calls `sem_wait()` before the child runs.
- 2nd case: child runs first to completion before parent calls `sem_wait()`.

# Producer/Consumer (bounded buffer) problem

## 1st attempt

```c
int buffer[MAX];
int fill = 0;
int use = 0;

void put(int value) {
    buffer[fill] = value;
    fill = (fill + 1) % MAX;
}

int get() {
    int tmp = buffer[use];
    use = (use + 1) % MAX;
    return tmp;
}

// =====

sem_t empty;
sem_t full;

void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&empty);
        put(i);
        sem_post(&full);
    }
}

void *consumer(void *arg) {
    int tmp = 0;
    while (tmp != -1) {
        sem_wait(&full);
        tmp = get();
        sem_post(&empty);
        printf("%d\n", tmp);
    }
}

int main() {
    // ...
    sem_init(&empty, 0, MAX); // initially, there are MAX empty slots
    sem_init(&full, 0, 0); // initially, there are no filled slots
    // ...
}
```

- Problem: **race condition**
  - Imagine 2 producers (P1 and P2) both calling into `put()`.
  - Assume P1 runs first and fills the 1st buffer entry.
  - Before P1 increments the `fill` counter to 1, it is interrupted.
  - P2 runs and also fills the 1st buffer entry, which overwrites the data published by P1.

## Add mutual exclusion

- The filling of the buffer and incrementing of the index is a **critical section** -> need locks.

```c
void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&mutex);
        sem_wait(&empty);
        put(i);
        sem_post(&full);
        sem_post(&mutex);
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&mutex);
        sem_wait(&full);
        int tmp = get();
        sem_post(&empty);
        sem_post(&mutex);
        printf("%d\n");
    }
}
```

- Problem: **deadlock**
  - Imagine 2 threads, 1 producer and 1 consumer.
  - The consumer runs first, acquires the lock, then `sem_wait()` on the `full` semaphore. There's no data yet, so the consumer blocks and yields the CPU. Importantly, it still holds the lock.
  - The producer then runs and tries to acquire the lock. But the lock is already held by the consumer.
  - **Cycle**: The consumer holds the mutex and is waiting for some thread to signal `full`. The producer could signal `full` but is waiting for the mutex.

## A working solution

- Reduce the scope of the lock: move the mutex acquire and release to be just around the critical section.

```c
void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&empty);
        sem_wait(&mutex);
        put(i);
        sem_post(&mutex);
        sem_post(&full);
    }
}

void *consumer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        sem_wait(&full);
        sem_wait(&mutex);
        int tmp = get();
        sem_post(&mutex);
        sem_post(&empty);
        printf("%d\n");
    }
}
```

# Reader-Writer locks

- Different data structure accesses might require different kind of locking.
- Example: Concurrent list operations
  - Inserts change the state of the list -> traditional critical section makes sense.
  - Lookups simply read the data structure -> as long as we can guarantee that no insert is on-going, we can allow many lookups to proceed concurrently.
- Reader-Writer lock:

```c
typedef struct _rw_lock_t {
    sem_t lock; // binary semaphore; protect the critical section of read lock acquire/release
    sem_t write_lock; // binary semaphore; allow 1 writer or many concurrent readers
    int readers; // number of readers in critical section
} rw_lock_t;

void rw_lock_init(rw_lock_t *rw) {
    rw->readers = 0;
    sem_init(&rw->lock, 0, 1);
    sem_init(&rw->write_lock, 0, 1);
}

void rw_lock_acquire_read_lock(rw_lock_t *rw) {
    sem_wait(&rw->lock);
    rw->reader++;
    if (rw->reader == 1) // first reader acquires write lock
        sem_wait(&rw->write_lock);
    sem_post(&rw->lock);
}

void rw_lock_release_read_lock(rw_lock_t *rw) {
    sem_wait(&rw->lock);
    rw->reader--;
    if (rw->reader == 0) // last reader releases write lock
        sem_post(&rw->write_lock);
    sem_post(&rw->lock);
}

void rw_lock_acquire_write_lock(rw_lock_t *rw) {
    sem_wait(&rw->write_lock);
}

void rw_lock_release_write_lock(rw_lock_t *rw) {
    sem_post(&rw->write_lock);
}
```

- Mechanism:
  - A single writer can acquire the write lock and enter the critical section to update the data structure.
  - The first reader also acquires the write lock. Thus, once a reader has acquired the read lock, more readers will be allowed to acquire the read lock, but all writers must wait until all readers are finished.
  - The last reader to exit the critical section releases the write lock and thus enables a waiting writer to proceed.

- Problem: **fairness**
  - It's easy for readers to starve writers.
- Solution: _How to prevent more readers from entering the lock once a writer is waiting?_
  - Add a `waiting_writers` counter and a condition variable.
  - Make new readers wait if a certain number of writers are waiting.
- Note: reader-writer locks often add more overhead and do not end up speeding up performance compared to simple and fast locking primitives.

# The dining philosophers's problem

- Setup:
  - There are 5 philosophers around a table.
  - Between each pair of philosophers is a single fork -> 5 forks.
  - In order to eat, a philosopher needs 2 forks, both the one on their left and the one on their right.
  - Problem: The contention for the forks.
- Basic loop of each philosopher, each has a unique thread identifier p (0 -> 4):

```c
while (1) {
    think();
    get_forks(p);
    eat();
    put_forks(p);
}
```

- Challenge: write `get_forks()` and `put_forks()` such that there is no deadlock, no philosopher starves and never gets to eat, and concurrency is high _(as many philosophers can eat at the same time as possible)_.
- Helpers:

```c
// ===== Forks that philosopher p needs =====

int left(int p) {
    return p;
}

int right(int p) {
    return (p + 1) % 5;
}

// Semaphores: assume 1 for each fork
sem_t forks[5];
```

## Broken solution

- Initialize each semaphore to 1.
- Routines to get/put forks:

```c
void get_forks(int p) {
    sem_wait(&forks[left(p)]);
    sem_wait(&forks[right(p)]);
}

void put_forks(int p) {
    sem_post(&forks[left(p)]);
    sem_post(&forks[right(p)]);
}
```

- Problem: **deadlock**
  - If each philosopher grabs the fork on the left before any philosopher can grab the lock on their right, each will be stuck holding 1 fork and waiting for another, forever.

## Solution: breaking the dependency

- Change how forks are acquired by at least 1 philosopher _(this is how Dijkstra himself solved the problem)_.
- Assume that philosopher 4 get the forks in a different order than the others.

```c
void get_forks(int p) {
    if (p == 4) {
        sem_wait(&forks[right(p)]); // right first
        sem_wait(&forks[left(p)]);
    } else {
        sem_wait(&forks[left(p)]); // left first
        sem_wait(&forks[right(p)]);
    }
}
```

# Thread throttling

- Problem: How do we prevent too many threads from doing something at once.
- Answer: Decide the "too many" threshold, and use a semaphore to limit the number of threads concurrently executing the code.
- This is called **throttling**, and is a form of **admission control**.
- Example:
  - In a certain part of the code, each thread requires a large amount of memory _(the memory-intensive region)_.
  - If all threads enter the memory-intensive region at the same time, the sum of required memory will exceed the the amount of physical memory. The machine will start thrashing _(spends most time swapping pages to and from the disk)_.

# How to implement semaphores

```c
typedef struct __Zem_t {
    int value;
    pthread_cond_t cond;
    pthread_mutex_t lock;
} Zem_t;

// only 1 thread should call this
void Zem_init(Zem_t *s, int value) {
    s->value = value;
    Cond_init(&s->cond);
    Mutex_init(&s->mutex);
}

void Zem_wait(Zem_t *s) {
    Mutex_lock(&s->lock);
    while (s->value <= 0) // we can actually use '== 0'
        Cond_wait(&s->cond, &s->lock);
    s->value--;
    Mutex_unlock(&s->lock);
}

void Zem_post(Zem_t *s) {
    Mutex_lock(&s->lock);
    s->value++;
    Cond_signal(&s->cond);
    Mutex_unlock(&s->lock);
}
```

- Use 1 lock and 1 condition variable, plus a state variable (`value`) to track the value of the semaphore.
- Difference between our Zemaphore and pure semaphores defined by Dijkstra:
  - We don't maintain the invariant that the value of the semaphore, when negative, reflects the number of waiting threads.
  - The value will never be lower than 0.
  - This behavior is easier to implement and matches current Linux implementation.
