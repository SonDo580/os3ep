- Problem: We need to execute a series of instructions atomically, but we couldn't due to the presence of interrupts.
- Solution: Put **locks** around critical sections.

# Basic idea

- Example:

```c
lock_t mutex;
// ...
lock(&mutex);
balance = balance + 1;
unlock(&mutex);
```

- A lock is either **available**(or **unlocked** or **free**) or **acquired** (or **locked** or **held**).
- Only 1 thread can hold the lock at any given time (the **owner**).

# `Pthread` locks

- lock <-> **mutex** (provide **mutual exclusion** between threads).
- Example:

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
// ...
Pthread_mutex_lock(&lock); // wrapper; exits on failure
balance = balance + 1;
Pthread_mutex_unlock(&lock);
```

- We often protect different data with different locks (**fine-grained** approach).

# Evaluating locks

- Provide **mutual exclusion**: Does the lock work, preventing multiple threads from entering the a critical section?
- **Fairness**: Does each thread contending for the lock get a fair shot at acquiring it once it is free?
- **Performance**: The time overhead added by using the lock
  - no contention (1 thread).
  - multiple threads contending for the lock.
  - when there are multiple CPUs.

# Controlling interrupts

- 1 solution: disable interrupts (using some kind of hardware instruction) for critical section.
- invented for single-processor systems.

- Pseudocode:

```c
void lock() {
    DisableInterrupts();
}
void unlock() {
    EnableInterrupts();
}
```

- Pros: simplicity
- Cons:
  - Allow any calling threads to perform a privileged operation (turning interrupts on and off) -> Malicious programs can call `lock()` and go into an infinite loop -> The OS never regains control of the system (must restart).
  - Does not work on multiprocessors: If multiple threads are running on different CPUs, each trying to enter the same critical section, disabling interrupts (for 1 CPU) doesn't prevent other threads from entering the critical section.
  - Lead to interrupts being lost, which can lead to serious system problems (Example: the CPU missed the fact that a disk device has finished a read request -> the OS cannot wake the waiting process).

- Usage: limited
  - In some cases the OS itself will use interrupt masking to guarantee atomicity when accessing its own data structures.

# Failed attempt: just using load/store

```c
typedef struct __lock_t {
    int flag;
} lock_t;

void init(lock_t *mutex) {
    // 0: available
    // 1: held
    mutex->flag = 0;
}

void lock(lock_t *mutex) {
    while (mutex->flag == 1) // TEST the flag
        ; // spin-wait
    mutex->flag = 1; // set flag (and enter critical section)
}

void unlock(lock_t *mutex) {
    mutex->flag = 0;
}
```

- Correctness problem (doesn't provide mutual exclusion). Example:
  - T1 sees that `flag == 0` and proceeds.
  - interrupt.
  - T2 sees that `flag == 0` and proceeds.
  - T2 sets `flag = 1` and enters critical section.
  - interrupt.
  - T1 sets `flag = 1` and enters critical section.
- Performance problem (**spin-waiting**):
  - wastes CPU cycles.
  - on uni-processor, the thread that the waiter is waiting for cannot even run (until a context switch occurs).

# Build working spin locks with `Test-And-Set`

- Need hardware support: **test-and-set** (or **atomic exchange**) instruction.
- Pseudocode:

```c
int TestAndSet(int *old_ptr, int new) {
    int old = *old_ptr; // fetch old value at old_ptr
    *old_ptr = new; // store ’new’ into old_ptr
    return old; // return the old value
}
```

- **Spin lock**:

```c
// ...

void lock(lock_t *mutex) {
    while (TestAndSet(&mutex->flag, 1) == 1)
        ; // spin-wait
}
```

- To work properly on a single processor, this requires a preemptive scheduler _(interrupt a thread via timer, in order to run a different thread)_.

# Evaluating spin locks

- Correctness: Yes
- Fairness: Don't provide any fairness guarantees, may lead to starvation _(A thread may spin forever under contention)_.
- Performance:
  - terrible on a single CPU: Imagine the thread holding the lock is preempted withing a typical section. The scheduler then runs every other thread, each of which tries to acquire the lock and spins for the duration of the time slice.
  - reasonably good on multiple CPUs (if the number of threads roughly equal the number of CPUs): The other threads will spin on different CPUs.

# `Compare-And-Swap`

- Pseudocode:

```c
int CompareAndSwap(int *ptr, int expected, int new) {
    int original = *ptr;
    if (original == expected)
        *ptr = new;
    return original;
}
```

- **Spin lock**:

```c
// ...

void lock(lock_t *mutex) {
    while (CompareAndSwap(&mutex->flag, 0, 1) == 1)
        ; // spin-wait
}
```

- **compare-and-swap** is a more powerful instruction than **test-and-set** (later).

# `Load-Linked` and `Store-Conditional`

- Pseudocode:

```c
int LoadLinked(int *ptr) {
    return *ptr;
}

int StoreConditional(int *ptr , int value) {
    if (no update to *ptr since LoadLinked to this address) {
        *ptr = value;
        return 1; // success
    } else {
        return 0; // failed
    }
}
```

- **Spin lock**:

```c
void lock(lock_t *mutex) {
    while (1) {
        while (LoadLinked(&mutex->flag) == 1)
            ; // spin util mutex->flag = 0

        if (StoreConditional(&mutex->flag, 1) == 1)
            return; // if set-to-1 was successful: done
                    // otherwise: try again
    }
}
```

- **Spin lock** (alternative):

```c
void lock(lock_t *mutex) {
    while (LoadLinked(&mutex->flag) ||
            !StoreConditional(&mutex->flag, 1))
        ; // spin
}
```

# `Fetch-And-Add`

- Pseudocode:

```c
int FetchAndAdd(int *ptr) {
    int old = *ptr;
    *ptr = old + 1;
    return old;
}
```

- **Ticket lock** (not mutex, still spin):

```c
typedef struct __lock_t {
    int ticket;
    int turn;
} lock_t;

void lock_init(lock_t *ticket_lock) {
    ticket_lock->ticket = 0;
    ticket_lock->turn = 0;
}

void lock(lock_t *ticket_lock) {
    int my_turn = FetchAndAdd(&ticket_lock->ticket);
    while (ticket_lock->turn != my_turn)
        ; // spin
}

void unlock(lock_t *ticket_lock) {
    ticket_lock->turn = ticket_lock->turn + 1;
}
```

- Difference from previous attempts: Ensure progress for all threads (**fairness**).

# Yield

- Problem of spinning: When a context switch occurs in a critical section, all other threads will just spin for their entire time slice, until the lock-holding thread runs again and release the lock.
- Need OS support: `yield()` system call
  - A thread can be in 1 of 3 states: **running**, **ready**, **blocked**. `yield()` moves the caller from **running** to **ready** state.
  - A thread can call this primitive when it wants to give up the CPU and let another thread run (**de-schedule** itself).

- Lock with `test-and-set` and `yield`:

```c
void init() {
    flag = 0;
}

void lock() {
    while (TestAndSet(&flag, 1) == 1)
        yield(); // give up the CPU
}

void unlock() {
    flag = 0;
}
```

- Evaluation:
  - Performance: better than spinning but still costly due to **context switching** overhead.
  - Fairness: doesn't address starvation.

# Using queues: sleeping instead of spinning

- Problems with some previous approaches: The scheduler determines which thread run next -> No prevention of starvation.
- We need OS support + a queue to keep track of which threads are waiting to acquire the lock.
- Support provided by Solaris:
  - `park()`: put a calling thread to sleep.
  - `unpark(thread_id)`: wake a particular thread.
- Lock with **queues**, `test-and-set`, `yield`, **wakeup**:

```c
typedef struct __lock_t {
    int flag;
    int guard;
    queue_t *q;
} lock_t;

void lock_init(lock_t *m) {
    m->flag = 0;
    m->guard = 0;
    queue_init(m->q);
}

void lock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ; // acquire guard lock by spinning
    if (m->flag == 0) {
        m->flag = 1; // lock is acquired
        m->guard = 0;
    } else {
        queue_add(m->q, gettid());
        m->guard = 0;
        park();
    }
}

void unlock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ; // acquire guard lock by spinning
    if (queue_empty(m->q))
        m->flag = 0; // release lock
    else
        unpark(queue_remove(m->q)); // (hold lock for next thread)
    m->guard = 0;
}
```

- Use a queue of waiters to avoid starvation.
- Use guard - a spin lock around the flag and queue manipulations the lock is using
  - Doesn't avoid spin-waiting entirely. A thread may be interrupted while acquiring or releasing the lock, and thus cause other threads to spin-wait.
  - However, the time spent spinning is limited _(just a few instructions inside the lock and unlock code, instead of the user-defined critical section)_.
- The flag does not get set back to 0 when another thread gets woken up. Why:
  - When a thread is woken up, it will be as if it is returning from `park()`.
  - However, it does not hold the guard at that point and cannot set the flag to 1.
  - Thus, we must pass the lock directly from the thread releasing the lock to the next thread acquiring it.
- Race condition (**wake-up/waiting race**):
  - T1 is about to `park()`.
  - A switch happen. T2 (which is holding the lock) releases the lock.
  - The subsequent `park()` makes T1 sleep forever (unless there's another thread releasing the lock).
- Solve race condition:
  - Solaris adds a 3rd system call: `setpark()`.
  - A thread T1 can indicate it is about to park by calling this routine. If it is interrupted right before `park()` and another thread T2 call `unpark(T1)`, the subsequent `park()` (in T1) returns immediately instead of sleeping.

```c
// ...

void lock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ;
    if (m->flag == 0) {
        m->flag = 1;
        m->guard = 0;
    } else {
        queue_add(m->q, gettid());
        set_park(); // new code
        m->guard = 0;
        park();
    }
}
```

# Linux's `futex`

- Code snippet from `lowlevellock.h` in nptl library (part of the gnu libc library)

```c
void mutex_lock(int *mutex) {
    int v;

    // bit 31 was clear, we got the mutex
    if (atomic_bit_test_set(mutex, 31) == 0)
        return;

    // add current thread to the queue
    atomic_increment(mutex);

    while(1) {
        // try to acquire the lock again
        if (atomic_bit_test_set(mutex, 31) == 0) {
            // success -> remove current thread from the queue
            atomic_decrement(mutex);
            return;
        }

        // Wait to make sure futex value is negative (locked)
        v = *mutex;
        if (v >= 0) {
            // lock has been released -> try acquiring again
            continue;
        }

        futex_wait(mutex, v);
        // - if v is still < 0, sleep.
        // - if lock has been released (v >= 0), returns immediately.
    }
}

void mutex_unlock(int *mutex) {
    // adding 0x80000000 (10...0) to counter results in 0 if and only if there are no other interested threads
    if (atomic_add_zero(mutex, 0x80000000))
        return;

    // There are other threads waiting for this mutex, wake one of them up
    futex_wake(mutex);
}
```

- Futex calls:
  - `futex_wait(address, expected)`: Puts the calling thread to sleep, assuming the value at 'address' is equal to 'expected'. If values are not equal, the call returns immediately.
  - `futex_wake(address)`: wakes 1 thread waiting on the queue
- Use a single integer to track whether the lock is held or not (the MSB) and the number of waiters on the lock (all other bits).
  - If the lock is negative (MSB = 1), it is held.
- Optimized when there is no contention for the lock: With only 1 thread acquiring and releasing the lock, very little work is done _(an atomic bit test-and-set to lock and an atomic add to release the lock)_.

# 2-phase lock

- A 2-phase lock realizes that spinning can be useful, if the lock is about to be released.
- In the 1st phase, the lock spins for a while, hoping that it can acquire the lock.
- If the lock is not acquired during the spin phase, a second phase is entered. The caller is put to sleep, and only woken up when the lock becomes free later.
- The Linux lock above is a form of 2-phase lock, but it only spins once (iteration). A generalization could spin in a loop for a fixed amount of time before using **futex** support to help.

# Extra

## Peterson's algorithm

- Just load and store are used.
- Ensure that 2 threads never enter a critical section at the same time.
- Code for 2 threads:

```c
int flag[2];
int turn;

void init() {
    // indicate you intend to hold the lock
    // (e.g., flag[0] = 1 -> thread 0 intends to hold the lock)
    flag[0] = flag[1] = 0;

    // whose turn is it? (thread 0 or 1)
    turn = 0;
}

void lock() {
    // indicate that you intend to hold the lock
    flag[self] = 1; // self is thread ID of caller

    // make it other thread's turn
    turn = 1 - self;

    while ((flag[1 - self] == 1) && (turn == 1 - self))
        ; // spin-wait while it's not your turn
}

void unlock() {
    // undo your intent
    flag[self] = 0;
}
```

- Example case 1:

```
Thread 0                        Thread 1
----------------------------------------
flag[0] = 1
turn = 1
flag[1] = 0 -> proceed
```

- Example case 2:

```
Thread 0                            Thread 1
-------------------------------------------------------------------
flag[0] = 1
turn = 1                                    
                                    flag[1] = 1
(flag[1] = 1, turn = 1) -> wait
                                    turn = 0
                                    (flag[0] = 1, turn = 0) -> wait
(turn = 0) -> proceed
```


- Example case 3:

```
Thread 0                            Thread 1
-------------------------------------------------------------------
flag[0] = 1
turn = 1                                    
                                    flag[1] = 1
                                    turn = 0
(turn = 0) -> proceed
```
