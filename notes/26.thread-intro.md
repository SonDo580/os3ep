- A **multi-threaded** program has more than 1 point of execution (multiple program counters).
- Threads for 1 process share the same address space.
- Each thread has its own private set of registers it uses for computation -> A **context switch** is needed to switch from running 1 thread to another (on a single core).
- **Context switch** for thread:
  - Save register state of T1 and restore register state of T2.
  - Need 1 **thread control block** (TCB) to store the state of each thread of a process.
  - The address space remains the same -> Don't need to switch page table.
- Need **1 stack per thread** in a multi-thread process.

# Why use threads

- **Parallelism**:
  - Example: Adding 2 large arrays -> If the system has multiple processors, we can let each processor performs a portion of the work.
  - The task of transforming a single-threaded program into a program that does this sort of work if called **parallelization**.
- Avoid blocking program progress due to slow I/O:
  - While a thread is blocked waiting for I/O, the CPU can switch to other threads to perform computation or issuing further I/O requests.

# Problem: shared data

- Example: `thread-intro/t1.c`
- Assembly code to update `counter` _(assumes `counter` is located at address 0x8049a1c)_.

```asm
mov 0x8049a1c, %eax
add $0x1, %eax
mov %eax, 0x8049a1c
```

- Problem: **race condition** (more specifically, **data race**). Example:
  - `counter` = 50.
  - T1 reads `counter` into `eax` -> `eax` = 50.
  - T1 increments `eax` -> `eax` = 51.
  - context switch: T1 -> T2.
  - T2 reads `counter` into `eax` -> `eax` = 50.
  - T2 increments `eax` -> `eax` = 51.
  - T2 saves `eax` back to `counter`-> `counter` = 51.
  - context switch: T1 -> T2.
  - T1 saves (restored) `eax` back to `counter` -> `counter` = 51.
  - Desired result: `counter` = 52.
- The code block above is a **critical section**:
  - A piece of code that access shared resource and must not be concurrently executed by more than 1 thread.
  - Multiple threads executing this code can result in race condition.
  - We need **mutual exclusion**.

# Guarantee atomicity

## Method 1: Atomic hardware instructions

- Have more powerful instructions that do what we need in a single step (cannot be interrupted).
- Example: `memory-add 0x8049a1c, $0x1`

## Method 2: Synchronization primitives

- Hardware provides a few useful instructions upon which we can build a general set of **synchronization primitives**.

# Problem: waiting

- A process/thread can be put to sleep while waiting for I/O. When the I/O completes, the process/thread needs to be waked up.
- Solution: **condition variables**.
