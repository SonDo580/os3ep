# "Old" Unix file system

- Data structures on disk:

```
| S | Inodes | Data |
```

- The super block contains information about the entire file system: how big the volume is, how many inodes there are, a pointer to the head of a free list of blocks, ...
- The inode region contains all inodes for the file system.
- Most of the disk was taken up by data blocks.
- The good:
  - Simple.
  - Support basic abstractions the file system was trying to deliver: files and the directory hierarchy.

# Problem: Poor performance

- Main issue: Treating the disk like random access memory -> Expensive positioning costs.
  - Example: The data block of a file is often very far away from its inode, inducing an expensive seek when one first read the inode and then the data blocks of a file.
- The file system would end up getting quite **fragmented**, as the free space was not carefully managed.
  - The free list would end up pointing to a bunch of blocks spread across the disk.
  - As files get allocated, simply take the next free block. The result is that a logically contiguous file would be accessed by going back and forth across the disk, reducing performance dramatically.
- Aside: disk **defragmentation** tools organize on-disk data to place files contiguously and make free space for contiguous regions
- Another problem: the original block size was too small (512 bytes).
  - Transferring data from disk was inefficient, as each block might require a positioning overhead to reach it.
  - Small blocks reduce **internal fragmentation** (waste within the block), but bad for transfers.

# FFS (Fast file system)

- Design the file system structures and allocation policies to be "disk aware" and thus improve performance.
- Keep the same interface to the file system: open(), read(), write(), close(), ...

# Organizing structure: The cylinder group

- FFS divides the disk into a number of cylinder groups.
  - A single cylinder is a set of tracks on different surfaces on the hard drive that are the same distance from the center.
  - FFS aggregates N consecutive cylinders into a group.
- Modern drives hide their geometry from clients. Thus, modern file systems instead organize the drive into **block groups**, each of which is a consecutive portion of the disk's address space.
- By placing 2 files within the same group, FFS can ensure that accessing one after the other will not result in long seeks across the disk.
- FFS includes all structures a file system have within each group: inodes, data blocks, per-group bitmaps, a copy of the super block.
- What FFS keeps within a single group:

```
| S | Inode bitmap | Data bitmap |Inodes | Data |
```

- FFS keeps a copy of the **super block** in each group for reliability reasons.

# Policies: How to allocate files and directories

- Place related stuff within the same block group, unrelated stuff in different block groups.
- Placement of directories: Find the group with a low number of allocated directories _(to balance directories across groups)_ and a high number of free inodes _(to subsequently be able to allocate a bunch of files)_, and put directory data and inode in that group.
- For files:
  - Make sure to allocate the data blocks of a file in the same group as its inode, thus preventing long seeks between inode and data.
  - Place all files in the same directory in the group of the directory they are in.
- The FFS policy heuristics is based on "common sense":
  - Files in a directory are often accessed together _(Example: compile a bunch of files and link them into a single executable)_.

# Large file exception

- A large file would entirely fill the block group is is placed within.
- Filling a group like this is undesirable, as it prevents subsequent related files from being placed within this group, and hurt file-access locality.
- For large files:
  - After some number of blocks are allocated into the first block group _(number of direct pointers in an inode)_, FFS places the next chunk of the file _(those pointed to by the first indirect block)_ in another block group, and so on.
- Problem: Spreading blocks of a file across the disk will hurt performance, particularly in the case of sequential file access.
- Solution: If chunk size is large enough, the file system will spend most of the time transferring data and a relatively little time seeking between chunks.
  - The technique of reducing an overhead by doing more work per overhead paid is called **amortization**.
- Trend in disk drives: transfer rate improves quickly, mechanical aspects improve slowly.
  -> Mechanical costs become relatively more expensive.
  -> To amortize the costs, you have to transfer more data between seeks.

# Other things about FFS

- Accommodating small files:
  - Problem: Many files were 2KB or so in size (back then). Using 4KB blocks is good for transferring data, but not good for space efficiency (**internal fragmentation**).
  - Solution:
    - Introducing **sub-blocks**, each has 512 bytes.
    - A small file would use sub blocks initially.
    - When the file acquires a full 4KB data, FFS will find a 4KB block, copy the sub blocks into it, and free the sub blocks for future use.
  - Problem: Require a lot of extra I/Os to perform the copy.
  - Solution: FFS modifies the `libc` library to buffer writes then issue them in 4KB chunks to the file system, avoiding the sub-block specialization in most cases.
- Introduce a disk layout that was optimized for performance:
  - Example: Blocks on a track: 0 -> 1 -> 2 -> ...
  - Problem: During sequential read, FFS would first issue a read to block 0. By the time the read was complete, and FFS issued a read to block 1, it was too late: Block 1 had rotated under the head and now the read to block 1 would incur a full rotation.
  - Solution: Use a different layout for blocks: 0 -> 6 -> 1 -> 7 -> ... (skipping over every other block)
    - FFS can figure out for a particular disk how many blocks it should skip in doing layout to avoid the extra rotations.
    - This technique is called **parameterization** _(FFS would figure out the specific performance parameters of the disk and use those to decide the layout scheme)_.
  - Problem: We only get 50% of peak bandwidth with the above layout _(must go around each track twice to read each block once)_.
  - Solution:
    - Modern disks read the entire track in and buffer it in an internal disk cache (the **track buffer**).
    - On subsequent reads to the track, the disk will just return data from the cache.
- Usability improvements:
  - **long file names**.
  - **symbolic link**.
  - atomic `rename()` operation.
