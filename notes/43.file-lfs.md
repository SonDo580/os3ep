- The motivation to develop the log-structured file system was based on the following the following observations:
  - **System memories are growing**: More data can be cached. Disk traffic increasingly consists of writes, as reads are serviced by the cache. Thus, file system performance is largely determined by its write performance.
  - **There is a large gap between random I/O performance and sequential I/O performance**.
  - **Existing file systems perform poorly on many common workloads**: For example, FFS would perform a large number of writes to create a new file of size 1 block _(1 for a new inode, 1 to update the inode bitmap, 1 to the directory data block that the file is in, 1 to the directory inode to update it, 1 the new data block of the new file, 1 to the data bitmap to mark the block as allocated)_. Although FFS places all of these block within the same block group, it incurs many seeks and rotational delays.
  - **File system are not RAID-aware**: For example, both RAID 4 and RAID 5 have the **small-write problem** where a logical write to a single block causes 4 physical I/Os to take place.
- An ideal file system would:
  - Focus on write performance.
  - Try to make use of sequential bandwidth of the disk.
  - Perform well on common workload that not only write data but also update on-disk metadata structures frequently.
  - Work well on RAIDs as well as single disks.
- **Log-structured file system**:
  - When writing to disk, LFS buffers all updates (including metadata) in an in-memory **segment**.
  - When the segment is full, it is written to disk in 1 long, sequential transfer to an unused part of the disk.
  - LFS never overwrites existing data.
  - Because the segments are large, the disk (or RAID) is used efficiently, and performance of the file system is great.

# Write to disk sequentially

- The basic idea is writing all updates (data blocks, inodes, ...) to the disk sequentially.

# Writing sequentially and effectively

- Example:
  - Write a single block to address A at time T.
  - Write to address `A + 1` but at time `T + delta`.
  - In between the first and second write, the disk has rotated. The disk will will wait `T_rotation - delta` before it can commit the second write to disk.
- Writing to disk in sequential order is not enough. You must issue a large number of contiguous writes (or 1 large write).
- To achieve this, LFS uses **write buffering**:
  - LFS keeps track of updates in memory.
  - When it has received a sufficient number of updates, it writes them to disk all at once.
- The large chunk of updates LFS writes at 1 time is called a **segment**.

# How much to buffer

- Depends on the disk: how high the positioning overhead is in comparison to the transfer rate.
- Assumptions:
  - Positioning before each write takes `T_position` seconds.
  - The disk transfer rate is `R_peak` MB/s.
  - We are writing out D MB.
- The time to write out this chunk of data:
  `T_write = T_position + D / R_peak`
- The effective rate of writing:
  `R_effective = D / T_write = D / (T_position + D / R_peak)`
- `R_effective = F * R_peak` where `0 < F < 1` (a typical F might be 0.9).
- `D = (F / 1 - F) * R_peak * T_position`

```
. R_effective = D / (T_position + D / R_peak) = F * R_peak
. D = F * R_peak * (T_position + D / R_peak)
. D = (F * R_peak * T_position) + (F * D)
. D = (F / (1 - F)) * R_peak * T_position
```

# Problem: Finding inodes

- In typical file system (like FFS, old Unix file system):
  - Finding inodes is easy since they are organized in an array and placed on disk at fixed locations.
- In LFS:
  - We scatter the inodes all throughout the disk.
  - We never overwrite in place, thus the latest version of an inode keeps moving.

# Solution through indirection: The inode map

- Introduce a **level of indirection** between inode numbers and inodes through a data structure called the **inode map (imap)**.
- The imap:
  - Maps an inode number to the disk address of the most recent version of the inode.
  - Often be implemented as a simple array, with 4 bytes (a disk pointer) per entry.
  - Any time an inode is written to disk, the imap is updated with its new location.
- The imap needs to be kept persistent. Where should it reside on disk?
  - It could live on a fixed part of the disk. But this would require updates to file structures to be followed by writes to the imap, and performance would suffer _(disk seeks between each update and the fixed location of the imap)_.
  - LFS places chunks of the inode map right next to where it writes all of the other new information.
  - Example: append a data block to a file k:
  ```
  | D | I[k]    | imap    |
  |   | b[0]:A0 | m[k]:A1 |
  A0  A1        A2
  ```

# Completing the solution: The checkpoint region

- How do we find the inode map, now that pieces of it are spread across the disk?
  - The file system must have some fixed and known location on disk to begin a file lookup.
- LFS has the **checkpoint region (CR)**:
  - The checkpoint region contains pointers to (addresses of) the latest pieces of the inode map, thus the inode map can be found by reading the CR first.
  - The checkpoint region is only updated periodically (every 30 seconds or so), so performance is not ill-affected.

  ```
  | imap[k..k+N]:A2 |    ....    | D | I[k]    | imap    |
  | CR              |            |   | b[0]:A0 | m[k]:A1 |
  0                              A0  A1        A2
  ```

# Reading a file from disk: Recap

- Assume we have nothing in memory to begin.
- Read in the checkpoint region from disk.
- The CR contains pointers (disk addresses) to the entire inode map -> Read in the entire inode map and caches it in memory.
- After this, when given an inode number of a file, lookup the inode disk address from the imap, and read the most recent version of the inode.
- To read blocks from the file, proceed like a typical Unix file system, by using direct pointers or indirect pointers as need be.

# What about directories

- Directory structure is identical to classic Unix file systems: A directory is just a collection of (name, inode number) pairs.
- Creating a file 'foo' in a directory:
  - LFS must write a new inode, some data, directory data and its inode.
  - New structures on disk:
  ```
  | D[k] | I[k]    | D[dir]   | I[dir]  |  imap     |
  |      | b[0]:A0 | (foo, k) | b[0]:A2 | m[k]:A1   |
  |      |         |          |         | m[dir]:A3 |
  A0     A1        A2         A3
  ```
- When accessing the file 'foo':
  - Look in the inode map (usually cached in memory) to find the location of the inode of directory 'dir' (A3).
  - Reading the directory inode gives you the location of the directory data (A2).
  - Reading this data block gives you the name-to-inode-number mapping (foo, k).
  - Consult the inode map again to find the location of the inode number k (A1).
  - Read the file inode then read the desired data block at address A0.
- **Recursive update problem**: arises in any file system that never updates in place, but moves update to new locations on disk.
  - When an inode is updated, its location on disk changes. This would have also entailed an update to the directory that points to this file, and so on, all the way up the file system tree.
  - Solved by the inode map: Even though the location of the inode may change, the change is never reflected in the directory. The imap structure is updated while the directory holds the same name-to-inode-number mapping.

# Problem: Garbage collection

- LFS repeatedly writes the latest version of a file (its inode and data) to new locations on disk.
- This keeps writes efficient, but leaves old versions of file structures scattered throughout the disk. These old versions are called **garbage**.
- What should we do with the old versions:
  - One could keep those older versions around and allow user to restore old file versions -> Such a file system is known as a **versioning file system**.
  - LFS only keeps the latest **live** version of a file. It must (in the background) periodically finds these old **dead** versions of file data, inodes, other structures, and **clean** them.
- Segments are the mechanism that enables large writes to disk in LFS. They are also integral to effective cleaning.
  - If the LFS cleaner simply went through and freed single blocks, the result is a file system with some number of free **holes**. Write performance would drop since LFS would not be able to find a large contiguous region to write to disk sequentially.
- Basic cleaning process:
  - Read in M existing segments.
  - Compact their contents into N new segments with only live blocks (N < M).
  - Write the N segments to disk in new locations.
  - Free the old M segments to be used for subsequent writes.

# Determine block liveness

- LFS adds a little extra information to each segment that describes each block.
  - For each data block D, include its inode number (which file it belongs to) and its offset (which block of the file this is).
  - The information is recorded in a structure at the head of the segment known as the **segment summary block**.
- Determine block liveness:
  - For a block D on disk at address A, look into the segment summary block and find its inode number N and offset T.
  - Look in the imap to find where N lives and read N from disk (perhaps it is already in memory).
  - Using the offset T, look into the inode (or some indirect block) to see where the inode thinks the Tth block of this file is on disk.
  - If it points to disk address A, block D is live. Otherwise, block D is dead.
  - Pseudo code:

  ```c
  (N, T) = SegmentSummary[A];
  inode = Read(imap[N]);
  if (inode[T] == A)
    // block D is active
  else
    // block D is garbage
  ```

  - Example: live block

  ```
  | segment summary | D | I[k]    | imap    |
  | A0:(k,0)        |   | b[0]:A0 | m[k]:A1 |
                    A0  A1        A2
  ```

- Determining liveness more efficiently:
  - When a file is truncated or deleted, increase its **version number** and record the new version number in the imap and the segment summary block.
  - LFS can short circuit the check described above by comparing the version number in the segment summary block with the version number in the imap.
    - If `version_segment < version_imap`: LFS instantly knows the block is dead without reading the inode from disk.
    - If `version_segment == version_imap`: LFS falls back to regular checking.

# Policy question: Which blocks to clean, and when?

- When to clean:
  - Periodically, during idle time.
  - Or when you have to because the disk is full.
- Which blocks to clean:
  - 1 approach is to clean cold segments sooner and hot segments later.
  - A **hot segment** is one in which the contents are being frequently overwritten.
    -> Wait a long time before cleaning, as more and more blocks are getting overwritten (in new segments) and thus being freed for use.
  - A **cold segment** may have a few dead blocks but the rest of its content are relative stable.

# Crash recovery and the log

- What happens if the system crashes while LFS is writing to disk?
- During normal operation, LFS buffers writes in a segment, and then _(when the segment is full, or when some amount of time has elapsed)_ writes the segment to disk.
- LFS organizes these writes in a **log**: The checkpoint region points to a head and tail segment, and each segment points to the next segment to be written.
- LFS also periodically updates the checkpoint region.
- Crashes could happen during either operations:
  - Write a segment.
  - Write the CR.
- To ensure CR update happens atomically:
  - LFS keeps 2 CRs, one at either end of the disk, and writes to them alternately.
  - When updating the CR with the latest pointers to the inode map and other information, LFS first writes out a header (with timestamp), then the body of the CR, and finally 1 last block (with timestamp).
  - If the system crashes during CR update, LFS detect this by seeing an inconsistent pair of timestamps.
  - LFS will always choose to use the most recent CR that has consistent timestamps.
- When a crash happens before the CR is updated:
  - Upon reboot, LFS can recover by reading in the last CR, the imap pieces it points to, and subsequent files and directories. However, the last many seconds of updates would be lost.
  - To improve, LFS tries to rebuild many of those segments through a technique called **roll forward**: Start with the last CR, find the end of the log included in that CR, read through the next segments _(written after the last CR)_ and apply valid updates _(update the in-memory imap and other file system structures)_.
  - The next CR update will officially recognize the new segments in the log and the new imap pieces.

# Summary

- Instead of overwriting files in places, LFS writes to an unused portion of the disk, then later reclaims that old space through cleaning. This is called **shadow paging** or **copy-on-write**.
- This enables highly efficient writing, as LFS can gather updates into an in-memory segment then write them out sequentially. The large writes that LFS generates are excellent for performance on many different devices.
- The downside is it generates garbage. One must clean old segments periodically.
- Some file systems got around the cleaning problem by turning it into a feature: Provide old versions of the file system via **snapshot**.
